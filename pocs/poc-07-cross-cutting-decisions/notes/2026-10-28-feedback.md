# Feedback: `POST /v1/feedback` onto the call's trace (2026-10-28)

Work package W3 of [the PoC-7 plan](../../../docs/plans/2026-10-28-poc-07-cross-cutting.md). Exit criteria 2, 5, and 6 (feedback part).

## The API

`POST /v1/feedback` on the public port (`chassis.server.feedback`). Mounted when `spec.feedback.enabled` is true and `spec.adapters.feedback` is not `none`. The `fake` and `local` profiles default to `none`, so their OpenAPI does not change. The `cloud` profile defaults to `langfuse`.

Body, strict, no other field:

| Field | Rule |
| ----- | ---- |
| `request_id` | required, 1 to 256 characters |
| `score` | a number from 0 (bad) to 1 (good). suggested: a thumbs down is 0, a thumbs up is 1 |
| `label` | optional, up to 64 characters |
| `comment` | optional, up to 2000 characters |
| `feedback_id` | optional, `[A-Za-z0-9._:-]{1,128}`. Default: 32 hex of sha256(request_id, subject) |

The subject is the caller's `request.state.principal.subject`, set by the auth middleware (W2). It is never read from the body.

| Answer | When |
| ------ | ---- |
| 202 `{feedback_id, trace_id}` | stored |
| 404 `unknown_request` | no finished run with this id for this agent, or the lookup expired |
| 409 `feedback_id_conflict` | the `feedback_id` was used for another request |
| 422 | the body fails validation |
| 501 `feedback_not_configured` | `NoFeedback` |
| 502 `feedback_rejected` | the store refused it |
| 503 `feedback_unavailable`, `state_unavailable`, `not_ready` | retryable, `Retry-After: 1` |

Errors are `{"detail": {"code", "message"}}` with a fixed message.

## How the chassis finds the trace

The chassis owns both ids, so the engine exposes nothing. After every run whose engine stream ended, an `on_finished` callback (`FeedbackLookup`) writes `chassis:feedback:v1:req:<agent>:<sha256(request_id)>` -> `{trace_id, agent}` into `StatePort`, with `ttl = spec.feedback.lookup_ttl_s` (suggested: 7 days). The key is scoped by agent and hashed, like the idempotency keys. This differs from the plan's `feedback:req:<request_id>`. In complete mode the write is done before the answer goes out. A replica keeps nothing: `test_poc07_fb_a_second_replica_sharing_only_state_takes_the_feedback`.

The first time a `feedback_id` is seen, its time and request id go to `chassis:feedback:v1:id:<agent>:<sha256(feedback_id)>`. A repeat sends that first time again, because Langfuse updates a score only for the same `id` and `timestamp`. To carry it, `Feedback` gained an optional `timestamp` field. The contract suite gained `test_a_timestamp_is_kept`.

## The Langfuse mapping

`LangfuseFeedback` (`chassis.adapters.langfuse`) uses plain httpx and no SDK. It sends `POST {LANGFUSE_BASE_URL or LANGFUSE_HOST}/api/public/scores` with HTTP Basic auth (public key, secret key).

Evidence: the `langfuse` SDK 5.0.4, installed in a scratch venv, generated client:

- `langfuse/api/scores/raw_client.py`: `create` posts `"api/public/scores"` with `json=CreateScoresRequest`. Its docstring: "Returns 202 if all scores are accepted, or 207 with accepted/rejected counts".
- `langfuse/api/scores/types/create_scores_request.py`: `CreateScoresRequest = typing.List[CreateScoreRequest]`. **The body is a list**, not one object as the plan assumed.
- `types/create_score_request.py`: `id`, `traceId`, `observationId`, `sessionId`, `name`, `value`, `comment`, `metadata`, `dataType`, `timestamp`, and others. The `timestamp` doc says: "To update an existing score, send it again with the same id and timestamp."
- `types/create_score_batch_response.py`: 202 is `{"message": "Accepted"}`. `create_score_batch_results.py`: 207 is `{accepted, rejected, errors: [{message}]}`.
- Reading back: there is no `GET /api/public/scores/{id}` in 5.x. It is `GET /api/public/v3/scores?id=...&fields=details,subject`, with `subject: {kind: "trace", id}` (`score_subject_v3.py`).
- `langfuse/_client/environment_variables.py`: `LANGFUSE_BASE_URL`, with `LANGFUSE_HOST` marked deprecated.

| Score field | From |
| ----------- | ---- |
| `id` | `feedback_id` (upsert) |
| `traceId` | `trace_id_hex(request.trace_id)` |
| `name` | `spec.feedback.score_name` (`user-feedback`) |
| `value`, `dataType` | `score`, `NUMERIC` |
| `comment` | the comment as written |
| `metadata` | `{request_id, label, subject}`, None values left out |
| `timestamp` | the first time the `feedback_id` was seen |

**The trace id holds.** Langfuse's trace id is the OTel trace id in 32 lowercase hex:

- `langfuse/_client/client.py` `create_trace_id`: "Trace IDs must be 32 lowercase hexadecimal characters".
- `_get_otel_trace_id`: `self._format_otel_trace_id(span_context.trace_id)`.
- `score_current_trace` scores with that id.
- `langfuse/_client/span_processor.py:320`: `trace_id = format_trace_id(span.context.trace_id)`.

The chassis's `traceparent` carries `trace_id_hex(ctx.trace_id)`. `test_poc07_fb_feedback_lands_on_the_runs_trace_in_the_sidecar_lane` checks that the workload's model call carries the same id. It depends on W1's `OtelTelemetry` exporting the `chassis.run` span with that trace id. W1 has to confirm this.

**One score, not two.** The label is not written as a second CATEGORICAL score (suggested). Two scores would break "one record per `feedback_id`" and could leave a 207 half-written. The label is in `metadata` and in the event.

**Errors.** A transport error, a 5xx, or a 429 is `feedback_unavailable` and retryable. Another 4xx, or a 207 with a refused score, is `feedback_rejected`. The adapter does not retry (suggested): the caller decides. The secret key never appears in `repr`, an error, or a log.

## The comment

The comment goes to Langfuse as written: the user gave it on purpose, to be read with the trace. The event carries it through `chassis.redaction.redact`. Logs and spans never hold it. A store error message is redacted before it is logged. The orchestrator must confirm this split, or redact the stored comment as well.

## What each engine must expose

Nothing. The scenario runs `echo-python` and `echo-langgraph` in the `sidecar` lane with one test body and no engine-specific code.

## Proposed event-catalog entry (for `backlog-changes.md`; the epic is not edited)

> `agents.feedback.received.v1`: a user's feedback on one finished call, stored on that call's trace. Producer: the chassis, after `POST /v1/feedback` answers 202, when `spec.feedback.events` is on (suggested default: off). CloudEvents 1.0 on `EventPort`. `source` is `/agents/<agent>`, `subject` is the `request_id`, and `dataschema` is `feedback.v0.json`. `traceparent` is on the call's trace. `partitionkey` is sha256(request_id). `id` is a uuid5 of the feedback's content, so a redelivery has the same id and a changed score has a new one. Payload: `feedback_id`, `request_id`, `trace_id`, `agent`, `score` (0 to 1), `label`, `comment` (regex-redacted), `subject`, `received_at`. Consumers: eval datasets (golden-set candidates from low scores), product analytics. At least once; a publish failure never changes the 202.
