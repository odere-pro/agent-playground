# What the chassis waves should change (criterion 8)

Date: 2026-10-30. For W2 (Chassis MVP) and W5 (Chassis completion).

## W2

- **Ship the platform packages.** A new agent reaches the platform through a `.platform` link to a checkout. It works, but every agent's CI needs that checkout. Publish `workload-a2a`, `agent-testkit`, and `fake-model-server`, and a pinned chassis image. This changes 025 H-10 and 059 H-15.
- **`chassis serve --profile fake` with no config file.** The plan suggested it; the kit writes a config instead.
- **`chassis serve --uds`.** The offline gate refuses TCP, so the kit starts the chassis through a launcher. A flag removes it.
- **`--proxy-port 0`, with the bound port reported.** The kit picks a free port and closes it, which leaves a small race.
- **Pin an agent to the platform's versions.** A fresh resolve took newer releases than the platform tested. `agentctl` exports the platform's `uv.lock` into the agent. Keep this when the packages ship.

## W5

- **Split `agent-testkit` from the template.** 024 CH-3 and 058 CH-8 hold. The kit's lane cases are a copy of `chassis_contracts`, because that package imports the chassis. Move them to a package that does not.
- **The kit drives the `sidecar` connector for every agent.** Remote engines run offline only up to their first model call. A remote fixture belongs here.
- **Copier updates.** `copier update` is wired through the answers file, and no update has been run yet.
- **Helm.** `agent-lib` renders the remote lane as two pods. Add it to the deploy path in 024 CH-3, and decide whether the workload stays a Deployment or becomes a `Sandbox`.
