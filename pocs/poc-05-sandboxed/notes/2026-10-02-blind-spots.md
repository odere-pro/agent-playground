# What the chassis cannot see or control in the remote lane (2026-10-02)

Exit criterion 10. Task T29. Status: draft. Written 2026-10-02, before the kind suites ran; updated 2026-10-09 with what the bring-up and the kind suites found ([sidecar suite](2026-10-08-sidecar-suite.md), [remote suite](2026-10-08-remote-suite.md)).

Each item names its threat-model id (H01 to H32, boundaries B1 to B12 in [the threat model](2026-10-02-threat-model.md)). Each says what the chassis sees instead, and who does see it. A claim cites a file, a test, or a note.

Decisions on 2026-10-02 that shape this note:

- T10, the in-pod probe workload, is dropped. Controls are checked from outside the pod: static manifest tests, `kubectl exec` of standard tools in our own pods, and the spike. Criterion 8 is "partly shown".
- PoC-5 runs no broker. H11 is a recorded exception ([the H11 note](2026-10-02-h11-queue-exception.md)).
- The cluster work could not run in the cloud container ([cloud host limits](2026-10-02-cloud-host-limits.md)). It runs on the user's Mac. The cluster facts below come from [the bring-up note](2026-10-02-bring-up.md) and [the spike](2026-10-02-kind-sandbox-spike.md), both run on that Mac.

## 2. Added by PoC-5: what is not logged or not enforced

- **NetworkPolicy drops are not logged on kindnet (H18, H19, H20, H30).** kindnet runs kube-network-policies and enforces ingress and egress (spike, question 2). It writes no line for a dropped packet. The only record is the caller's timeout. The kind suites confirm it: every refused edge (H03, H04, H18, H19, H20, H30) shows up only as a connect timeout in the test, and no log on the node names it. Who would see it: a CNI with flow logs (suggested: Cilium with Hubble, or Calico flow logs). Source: plan section 5, "Where results are logged", item 4.
- **The trusted list is a hand-kept ConfigMap (B9, admission rule 4).** `trustedRepositories` in `agent-trust-params` (`deploy/kind/poc05/admission/params.yaml`) is typed by a platform admin. It is not registry metadata and not a signature. The chassis sees only `spec.trust` and reports it in `/manifest`. The API server sees the rule's refusal. Owner: 025 H-10 (contract v4, "Known gaps").
- **A third-party tool server may ignore the idempotency key (B11).** The chassis always sends the key in the call's `_meta`. It adds the key as a tool argument only when the tool's input schema declares that argument (`McpGatewayTools.call` in `packages/chassis/src/chassis/adapters/mcp/gateway.py`). The gateway does not forward `_meta` (bring-up, item 3). So a write tool whose schema does not declare the argument never gets the key. Our fake server and the code runner declare it and honor it. A server we do not own may not. Then a retried write runs twice, and the chassis cannot tell. Only that server's own logs show it.
- **The code runner's result cache is in memory (B11, B12).** `ResultCache` in `packages/code-runner/src/code_runner/server.py` keeps up to 256 results by idempotency key (`CACHE_SIZE`, suggested). A restart or a new sandbox loses it, and a retried call runs again. The oldest key is dropped past the size (`packages/code-runner/tests/test_code_runner_server.py::test_code_runner_forgets_the_oldest_key_past_the_cache_size`). Isolation between calls is per process, not per sandbox (security review, F5). The chassis sees one tool result per call.
- **DNS in the sidecar lane (H20).** The sidecar workload shares the pod's network namespace, so it inherits the chassis's DNS edge to kube-dns (security review, "DNS only where needed"). A name lookup can carry data out through kube-dns. The remote pod has no DNS at all: `getaddrinfo` fails and TCP to 10.96.0.10:53 times out (bring-up, item 7). The remote suite shows it with a control: the remote's A query to kube-dns (ClusterIP and a CoreDNS pod IP) and to 1.1.1.1 times out, while the same query from its chassis is answered (`test_poc05_kind_remote_controls.py::test_h20_remote_has_no_dns`). So DNS cannot tunnel out of the remote lane, and the tunneling caveat holds only in the sidecar lane. Static check: `pocs/poc-05-sandboxed/tests/test_poc05_netpol_static.py::test_poc05_netpol_dns_only_for_the_listed_pods`. Nobody logs the lookups. That is one more reason untrusted code goes remote.
- **The metadata address cannot be shown refused on kind (H01, B3).** Nothing answers at 169.254.169.254 on Docker Desktop, even with no policy (spike, question 2 and "not proven"). A timeout there proves nothing. What PoC-5 has instead: a static check that no rule allows it (`test_poc05_netpol_static.py::test_poc05_netpol_no_rule_can_reach_metadata_or_api` and `::test_poc05_netpol_checks_bite_ipblock`), the same check against the live policies on kind (`test_poc05_kind_sidecar_controls.py::test_h01_metadata_address_denied`: no live policy in a `poc05-*` namespace holds the address, so default deny applies), and this stated limit. H01 is static only on kind, even in the kind suite. The real proof needs a cloud node with a metadata service.
- **The PID limit is checked as set, not exhausted (H23, B10).** `podPidsLimit: 256` is in `deploy/kind/poc05/cluster.yaml` (line 23). Under gVisor, hitting it kills the whole sandbox and the pod restarts (`SandboxChanged`), instead of failing one `fork` (spike, question 6). So no PoC-5 check runs a process loop to the cap. The spike measured it on its own cluster. The code runner's `RLIMIT_NPROC` was shown in its pod: refused after 31 forks (bring-up, item 8). The static check of the cap is `pocs/poc-05-sandboxed/tests/test_poc05_pids_static.py`. It reads the value as set; it does not exhaust it. The cap is visible only on the node. Inside the gVisor sandbox `/sys/fs/cgroup/pids/pids.max` reads `max`: gVisor's own cgroup view does not show it. The remote suite reads `pids.max` 256 from the pod's cgroup on the node (`test_poc05_kind_remote_controls.py::test_h23_pids_cap_is_the_configured_limit`). So a remote cannot learn its own process budget, and the chassis does not see it either.

- **`/dev/shm` is writable in the sandbox (H21, H22, B10).** Inside the gVisor sandbox `/dev/shm` is gVisor's own tmpfs, and the remote can write there. It is not on the read-only root and has no `sizeLimit` of its own. What it holds counts against the pod's memory, so the memory limit caps it, not a disk cap. Not a finding for H21: the root stays read-only (remote suite, "Limits and observations"). The chassis does not see it. The kubelet sees only the pod's memory. Recorded for the gVisor note (T23).
- **A fork burst restarts the code runner (H23, B10, B11).** On 2026-10-09 the code runner's fork test ran into the pod's memory, not its process limit. Under gVisor each forked Python child costs 5 to 8 MiB, and 31 of them reach the 256Mi limit. Near the limit each fork takes seconds, and the burst restarted the code-runner pod (bring-up note, 2026-10-09). The test now execs `cat` in each child (`test_poc05_kind_code_runner.py`). A tool call can still make the sandbox restart. Then every call in flight fails, and the result cache is lost (the item above). The chassis sees a failed or timed-out tool call. The kubelet sees the restart. Owner: pending security review.
- **The gateway renames tools to `<server>-<tool>` (B11, H08).** LiteLLM's MCP gateway lists `fake_tools-glossary_lookup`, not `glossary_lookup` (bring-up, item 3). The chassis's `/mcp` passes these names on unchanged (sidecar suite, "Limits and observations"). The gateway also answers a bare name, but the chassis adapter adds the `idempotency_key` argument only for a name it listed, so a write tool called by its bare name loses the key (bring-up, "Requests"). The allow-list in `seed.sh` uses bare tool names per server. The name a workload sees, the name in the key's permission, and the name in a tool's own log differ. Nobody checks that they map to the same tool.

## 3. Added by PoC-5: what was not run, or stays open

- **H31, tag spoofing, not run.** The budget binds to the virtual key, not the `agent:<name>` tag a caller sends: `seed.sh` puts the tag in the key's `metadata.tags` (plan section 2.9; bring-up, item 2). No test sends a spoofed tag. 004 G-2's criterion "counted under the agent of its key" stays open. LiteLLM sees the key; the chassis sees the run.
- **H32, a managed runtime with its own key, not run.** It is PoC-6b's (plan section 5, last paragraph). See section 1: the chassis sees none of those calls.
- **B12, per-caller scope, open (PoC-8).** One Valkey ACL user with `~*` serves every caller (security review, B table). Tool idempotency keys are scoped to agent and request (`packages/chassis/tests/test_tool_idempotency.py`, M1), not to a caller. Do not claim B12 closed.
- **The TypeScript template has no token flag.** `packages/workload-a2a` has `--require-token-env` and `--previous-token-env` (T05). `echo-typescript` only sends `CHASSIS_API_TOKEN` on its outbound model call (`packages/workloads/echo-typescript/README.md`). Its A2A server checks no inbound token. So a TypeScript engine cannot be a remote yet (H17's workload half). Plan section 2.4 moves it to PoC-6.
- **In-pod checks from outside the pod only (T10 dropped; criterion 8 partly shown).** The probe workload `packages/workloads/hostile` is an empty skeleton. The kind suites check the controls from outside instead: `kubectl exec` of the image's own Python in our own containers, the live pod spec, and the node's cgroup. Every refusal has its paired control in the same test.
  - Sidecar, from the `agent-echo` workload container ([sidecar suite](2026-10-08-sidecar-suite.md)): hard requirement 1 for LiteLLM (H05), the MCP gateway (H07), Valkey (H10), and MinIO; H02, H25, H26; H13 (the kind half); H03 and H04; H01 static only (section 2).
  - Remote, from the `remote-echo` container and the node ([remote suite](2026-10-08-remote-suite.md)): H17, H18, H19 (a literal outside address, not DNS), H20, H21 (EROFS on `/var/tmp`), H23 (the cap as set), H28, H30, and the one-secret check. The code runner: gVisor, no egress, and `RLIMIT_NPROC`.
  - H17's in-run 200 is shown through the run the chassis opens, not by a call of ours inside it. A kind run is too short to time a second caller into it without a race (remote suite).
  - H08 on the cluster: the gateway refuses an unlisted tool for the chassis's key as `tool_denied` (`test_poc05_kind_tool_gateway.py`; bring-up, "Kind tier").
  - Still offline only: H14, H15, H16, H29.
  - Still static only, with no in-pod run: H09, H22, H24, H27. No code in our own images tries a setuid binary, a memory balloon, or a `/tmp` fill.
  - The H11 exception's closing step uses the sidecar workload container (`kubectl exec`, the image's Python), paired with the chassis publishing ([the H11 note](2026-10-02-h11-queue-exception.md)).
  - None of this replaces a probe that runs hostile code in the remote pod. The checks show the controls are there; they do not show what a determined workload can do inside them.
- **A refused model route reaches the remote as HTTP 500 `http_401` (H29).** LiteLLM refuses a route the key does not list. The adapter raises `ModelError("http_401", retryable=False)`, and the model proxy sends every non-retryable model error as 500. The remote cannot tell "you may not" from "the chassis broke". Test: `test_poc05_hostile_offline.py::test_h29_a_route_outside_the_key_is_refused_and_an_in_scope_call_is_200` (asserts `== 500` and `http_401`, so a change to this question fails the test). Open question in contract v4, owner `chassis-architect` (suggested: PoC-6).
- **No queue in PoC-5 (H11).** No broker runs on kind. Every PoC-5 agent config keeps `events: none` (`test_poc05_events_agnostic.py::test_poc05_agent_configs_run_no_broker`). No test on any stack shows a broker refusing a client without a credential. The PoC-4 Compose Kafka has no auth. Owner: `platform-security`, closing in 020 X-8 ([the H11 note](2026-10-02-h11-queue-exception.md)).
