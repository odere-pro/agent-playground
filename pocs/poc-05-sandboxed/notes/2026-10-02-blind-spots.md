# What the chassis cannot see or control in the remote lane (2026-10-02)

Exit criterion 10. Task T29. Status: draft. Written 2026-10-02, before the kind suites ran; updated 2026-10-09 with what the bring-up and the kind suites found ([sidecar suite](2026-10-08-sidecar-suite.md), [remote suite](2026-10-08-remote-suite.md)), and with the code runner's move to a sandbox per call ([per-call plan](../../../docs/plans/2026-10-09-poc-05-per-call-sandbox.md), task 7).

Each item names its threat-model id (H01 to H32, boundaries B1 to B12 in [the threat model](2026-10-02-threat-model.md)). Each says what the chassis sees instead, and who does see it. A claim cites a file, a test, or a note.

Decisions that shape this note:

- On 2026-10-02, T10 (the in-pod probe workload) was dropped and H11 (the queue) became a recorded exception ([the H11 note](2026-10-02-h11-queue-exception.md)). On 2026-10-09 the user reversed the H11 decision: Kafka with SASL runs on kind, and H11 passed ([close runs](2026-10-09-close-runs.md), section 3). T10 is a recorded exception, work in progress, owner the user ([the T10 note](2026-10-09-t10-probe-exception.md)). Results go in section 3.
- On 2026-10-09 the user chose a sandbox per call for the code runner ([per-call plan](../../../docs/plans/2026-10-09-poc-05-per-call-sandbox.md)). A dispatcher in `poc05-platform` takes each call, claims a fresh gVisor pod from a warm pool of 2, runs the code there, and deletes the claim.
- The cluster work could not run in the cloud container ([cloud host limits](2026-10-02-cloud-host-limits.md)). It runs on the user's Mac. The cluster facts below come from [the bring-up note](2026-10-02-bring-up.md) and [the spike](2026-10-02-kind-sandbox-spike.md), both run on that Mac.

## 2. Added by PoC-5: what is not logged or not enforced

- **NetworkPolicy drops are not logged on kindnet (H18, H19, H20, H30).** kindnet runs kube-network-policies and enforces ingress and egress (spike, question 2). It writes no line for a dropped packet. The only record is the caller's timeout. The kind suites confirm it: every refused edge (H03, H04, H18, H19, H20, H30) shows up only as a connect timeout in the test, and no log on the node names it. Who would see it: a CNI with flow logs (suggested: Cilium with Hubble, or Calico flow logs). Source: plan section 5, "Where results are logged", item 4.
- **The trusted list is a hand-kept ConfigMap (B9, admission rule 4).** `trustedRepositories` in `agent-trust-params` (`deploy/kind/poc05/admission/params.yaml`) is typed by a platform admin. It is not registry metadata and not a signature. The chassis sees only `spec.trust` and reports it in `/manifest`. The API server sees the rule's refusal. Owner: 025 H-10 (contract v4, "Known gaps").
- **A third-party tool server may ignore the idempotency key (B11).** The chassis always sends the key in the call's `_meta`. It adds the key as a tool argument only when the tool's input schema declares that argument (`McpGatewayTools.call` in `packages/chassis/src/chassis/adapters/mcp/gateway.py`). The gateway does not forward `_meta` (bring-up, item 3). So a write tool whose schema does not declare the argument never gets the key. Our fake server and the code runner declare it and honor it. A server we do not own may not. Then a retried write runs twice, and the chassis cannot tell. Only that server's own logs show it.
- **The code runner's result cache is in memory, in the dispatcher (B11).** `ResultCache` (`packages/code-runner/src/code_runner/server.py`) keeps up to 256 results by idempotency key (`CACHE_SIZE`, suggested). Since the per-call change the dispatcher holds it (`code_runner/dispatch.py`), not the sandbox. A dispatcher restart loses it, and a retried call runs again. A failed call frees its key, so its retry runs in a fresh sandbox. The oldest key is dropped past the size (`packages/code-runner/tests/test_code_runner_server.py::test_code_runner_forgets_the_oldest_key_past_the_cache_size`). The chassis sees one tool result per call.
- **The code runner is a sandbox per call (B10, B12, H23).** This replaces "isolation per process, one long-lived pod" (security review, F5) and "a fork burst restarts the code runner". The dispatcher creates a `SandboxClaim` on the warm pool `code-runner` (2 pods, suggested), calls `run_python` on the claimed pod's IP, and deletes the claim, which deletes the pod. A pod is never reused. On kind: a 31-child Python burst leaves the dispatcher up and the next call works (`test_poc05_kind_code_runner.py::test_python_child_burst_leaves_the_dispatcher_up`); call B sees neither `/tmp` nor `/dev/shm` files from call A, on another host (`::test_files_do_not_cross_calls`); the claim and its pod are gone within 10 s (`::test_claim_is_gone_after_the_call`) ([remote suite](2026-10-08-remote-suite.md), 2026-10-09). In 1 run of 3, at load 4.7, the call after the burst got `sandbox_lost` (same note). The fix is `0399a04`: the dispatcher retries a connect timeout to a fresh sandbox, proven offline (`packages/code-runner/tests/test_code_runner_dispatch.py`). On kind it did not recur in 10 runs at a 1-minute load under 2, with 110 dispatches and no `sandbox_lost` ([close runs](2026-10-09-close-runs.md), section 5). The retry was not seen firing on kind; a `connect_retry` log line is being added. The chassis sees a tool result or a `sandbox_unavailable` or `sandbox_lost` error. The kubelet sees the pods come and go.
- **Deleting a claim is a denial of service (B11).** The dispatcher's service account may `create`, `get`, and `delete` any `SandboxClaim` in `poc05-tools`. A stolen dispatcher token can delete other callers' claims. Their calls end with `sandbox_lost`. It cannot pick a template or pool, change a claim, or reach another namespace (the `can-i` list in the [bring-up note](2026-10-02-bring-up.md), 2026-10-09). The ResourceQuota caps it at 4 claims and 6 pods. The chassis sees a retryable tool error. Nobody logs who deleted a claim, short of API server audit logs, which kind does not keep.
- **The agent-sandbox controller may write NetworkPolicies cluster-wide (B2, B9).** Its upstream ClusterRole `agent-sandbox-controller-extensions` holds `networkpolicies` write in every namespace. With `networkPolicyManagement: Managed` it would write a policy that allows internet egress. We set `Unmanaged`, and admission rule T1 refuses any other template (`admission/extension-policy.yaml`). On kind no `poc05-*` NetworkPolicy has a template owner (bring-up note, 2026-10-09). We keep the upstream role; its breadth is a recorded trust in the controller. A compromised controller could open any namespace. The chassis does not see policies at all.
- **One `ipBlock`: the dispatcher reaches the API server (B4).** The dispatcher's egress to the API endpoint, a `/32` on 6443, is the one `ipBlock` in PoC-5 and a recorded B4 exception ([threat model](2026-10-02-threat-model.md), section 7). Sandboxes, workloads, and remotes still reach no API address.
- **DNS in the sidecar lane (H20).** The sidecar workload shares the pod's network namespace, so it inherits the chassis's DNS edge to kube-dns (security review, "DNS only where needed"). A name lookup can carry data out through kube-dns. The remote pod has no DNS at all: `getaddrinfo` fails and TCP to 10.96.0.10:53 times out (bring-up, item 7). The remote suite shows it with a control: the remote's A query to kube-dns (ClusterIP and a CoreDNS pod IP) and to 1.1.1.1 times out, while the same query from its chassis is answered (`test_poc05_kind_remote_controls.py::test_h20_remote_has_no_dns`). So DNS cannot tunnel out of the remote lane, and the tunneling caveat holds only in the sidecar lane. Static check: `pocs/poc-05-sandboxed/tests/test_poc05_netpol_static.py::test_poc05_netpol_dns_only_for_the_listed_pods`. Nobody logs the lookups. That is one more reason untrusted code goes remote.
- **The metadata address is refused live on kind, but not against a real metadata service (H01, B3).** Nothing answers at 169.254.169.254 on Docker Desktop by default (spike, question 2). Since 2026-10-09 a fixture puts that address on the kind node's loopback with a one-line HTTP listener. The sidecar workload's connect times out; an unpoliced pod in `default` gets the listener's 200 from the same address (`test_poc05_kind_sidecar_controls.py::test_h01_metadata_address_denied`; [remote suite](2026-10-08-remote-suite.md), 2026-10-09). The static check still holds: no rule can allow the address (`test_poc05_netpol_static.py::test_poc05_netpol_no_rule_can_reach_metadata_or_api`). What stays blind: a cloud metadata service answers on the node's link-local route, not on loopback, and holds real credentials. That needs a rerun on a cloud node (038 X-1a).
- **The PID limit is checked as set, not exhausted (H23, B10).** `podPidsLimit: 256` is in `deploy/kind/poc05/cluster.yaml` (line 23). Under gVisor, hitting it kills the whole sandbox and the pod restarts (`SandboxChanged`), instead of failing one `fork` (spike, question 6). So no PoC-5 check runs a process loop to the cap. The spike measured it on its own cluster. The code runner's `RLIMIT_NPROC` was shown in its pod: refused after 31 forks (bring-up, item 8). The static check of the cap is `pocs/poc-05-sandboxed/tests/test_poc05_pids_static.py`. It reads the value as set; it does not exhaust it. The cap is visible only on the node. Inside the gVisor sandbox `/sys/fs/cgroup/pids/pids.max` reads `max`: gVisor's own cgroup view does not show it. The remote suite reads `pids.max` 256 from the pod's cgroup on the node (`test_poc05_kind_remote_controls.py::test_h23_pids_cap_is_the_configured_limit`). So a remote cannot learn its own process budget, and the chassis does not see it either.

- **`/dev/shm` under gVisor ignores the pod's size cap (H22, B10).** runsc mounts its own tmpfs at `/dev/shm` (about 4 GiB in `df`), over the pod's `emptyDir`. It is not on the read-only root, so H21 holds.
  - Code runner: the template's 8Mi `emptyDir` is ignored. One call wrote 17 MiB with no error. Accepted by `platform-security`, owner 055 CH-6. Two bounds hold instead: the pod's 256Mi memory limit, and a fresh pod per call (`test_poc05_kind_code_runner.py::test_dev_shm_is_bounded_by_the_per_call_pod`, `::test_files_do_not_cross_calls`). `::test_dev_shm_is_capped` stays `xfail(strict=True)` with the evidence ([remote suite](2026-10-08-remote-suite.md), 2026-10-09).
  - `remote-echo`: the same. A 1 MiB write works; a 40 MiB fill gets no error and leaves nothing behind. The 32 MiB cap is `test_poc05_kind_remote_shm.py::test_dev_shm_is_capped_at_32mi`, a strict xfail. The bound that holds is the pod's 256Mi memory limit, enforced on the node (`::test_remote_pod_memory_limit_bounds_dev_shm`); the worst case is the remote taking down its own pod. Accepted, owner 055 CH-6 ([close runs](2026-10-09-close-runs.md), section 6).
  - The chassis does not see `/dev/shm` use. The kubelet sees only the pod's memory.
- **The gateway renames tools to `<server>-<tool>` (B11, H08).** LiteLLM's MCP gateway lists `fake_tools-glossary_lookup`, not `glossary_lookup` (bring-up, item 3). The chassis's `/mcp` passes these names on unchanged (sidecar suite, "Limits and observations"). The gateway also answers a bare name, but the chassis adapter adds the `idempotency_key` argument only for a name it listed, so a write tool called by its bare name loses the key (bring-up, "Requests"). The allow-list in `seed.sh` uses bare tool names per server. The name a workload sees, the name in the key's permission, and the name in a tool's own log differ. Nobody checks that they map to the same tool.

## 3. Added by PoC-5: what was not run, or stays open

- **H31, tag spoofing, not run.** The budget binds to the virtual key, not the `agent:<name>` tag a caller sends: `seed.sh` puts the tag in the key's `metadata.tags` (plan section 2.9; bring-up, item 2). No test sends a spoofed tag. 004 G-2's criterion "counted under the agent of its key" stays open. LiteLLM sees the key; the chassis sees the run.
- **H32, a managed runtime with its own key, not run.** It is PoC-6b's (plan section 5, last paragraph). See section 1: the chassis sees none of those calls.
- **B12, per-caller scope, open for Valkey (PoC-8).** For the code runner B12 is closed: a fresh sandbox per call (section 2). One Valkey ACL user with `~*` serves every caller (security review, B table). Tool idempotency keys are scoped to agent and request (`packages/chassis/tests/test_tool_idempotency.py`, M1), not to a caller. Do not claim B12 closed for Valkey.
- **The TypeScript template has no token flag, so it is a gVisor exception for criterion 9.** `packages/workload-a2a` has `--require-token-env` and `--previous-token-env` (T05). `echo-typescript` only sends `CHASSIS_API_TOKEN` on its outbound model call (`packages/workloads/echo-typescript/README.md`). Its A2A server checks no inbound token. So a TypeScript engine cannot be a remote yet (H17's workload half), and gVisor was not run for it. Criterion 9 lists it as an exception. Plan section 2.4 moves it to PoC-6.
- **Envoy as an egress proxy is not built.** It is an optional scope item (README). The chassis proxies add the credentials for models and tools, so no PoC-5 path needs it. Without it, no allow-listed outside host exists, and nothing can tell use from abuse on DNS where DNS is allowed (H20).
- **In-pod checks: the probe workload is a recorded exception (T10, criterion 8).** T10 is work in progress, owner the user ([the T10 note](2026-10-09-t10-probe-exception.md)). Criterion 8 closes flagged, "partly shown". Until the probe lands, the kind suites check the controls from outside: `kubectl exec` of the image's own Python in our own containers, the live pod spec, and the node's cgroup. Every refusal has its paired control in the same test.
  - Sidecar, from the `agent-echo` workload container ([sidecar suite](2026-10-08-sidecar-suite.md)): hard requirement 1 for LiteLLM (H05), the MCP gateway (H07), Valkey (H10), and MinIO; H02, H25, H26; H13 (the kind half); H03 and H04; H01 against a listener on the node (section 2).
  - Remote, from the `remote-echo` container and the node ([remote suite](2026-10-08-remote-suite.md)): H17, H18, H19 (a literal outside address, not DNS), H20, H21 (EROFS on `/var/tmp`), H23 (the cap as set), H28, H30, and the one-secret check. The code runner: gVisor, no egress, `RLIMIT_NPROC`, ingress only from the dispatcher, and the per-call items in section 2.
  - H17's in-run 200 is shown through the run the chassis opens, not by a call of ours inside it. A kind run is too short to time a second caller into it without a race (remote suite).
  - H08 on the cluster: the gateway refuses an unlisted tool for the chassis's key as `tool_denied` (`test_poc05_kind_tool_gateway.py`; bring-up, "Kind tier").
  - Still offline only: H14, H15, H16, H29.
  - Still static only, with no in-pod run: H09, H22, H24, H27. No code in our own images tries a setuid binary, a memory balloon, or a `/tmp` fill.
  - H11 runs from the workload container of `agent-echo-events` (`kubectl exec`, the image's Python), paired with the chassis publishing (`test_poc05_kind_hardreq1.py::test_kafka_refuses_the_workload_without_the_chassis_credential`).
  - None of this replaces a probe that runs hostile code in the remote pod. The checks show the controls are there; they do not show what a determined workload can do inside them. That is what the probe workload above is for, once built.
- **A refused model route reaches the remote as HTTP 500 `http_401` (H29).** LiteLLM refuses a route the key does not list. The adapter raises `ModelError("http_401", retryable=False)`, and the model proxy sends every non-retryable model error as 500. The remote cannot tell "you may not" from "the chassis broke". Test: `test_poc05_hostile_offline.py::test_h29_a_route_outside_the_key_is_refused_and_an_in_scope_call_is_200` (asserts `== 500` and `http_401`, so a change to this question fails the test). Open question in contract v4, owner `chassis-architect` (suggested: PoC-6).
- **The queue: H11 passed on kind.** On 2026-10-02 H11 was a recorded exception ([the H11 note](2026-10-02-h11-queue-exception.md)). On 2026-10-09 the user brought it back into scope. Kafka runs on kind with SASL/SCRAM and no PLAINTEXT listener. A login with no credential, an unknown user, and a guessed password each get the broker's error 58, and the chassis's own publish lands on its topic (`test_poc05_kind_hardreq1.py::test_kafka_refuses_the_workload_without_the_chassis_credential`; [close runs](2026-10-09-close-runs.md), section 3). Still blind: there is no authorizer, so the chassis user can read, create, and delete any topic; event payloads cross in clear (SASL_PLAINTEXT); TLS and per-service ACLs are 020 X-8's. The PoC-4 Compose Kafka still has no auth.
