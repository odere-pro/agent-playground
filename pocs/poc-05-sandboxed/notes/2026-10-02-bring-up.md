# PoC-5 bring-up on kind (T19, 2026-10-02)

What it took to get the whole PoC-5 stack running on the kind cluster `poc05`, and what only the cluster could settle. Host: macOS arm64, Docker Desktop VM 7.75 GiB, 14 CPUs; the user's `paligo-*` stacks kept running (about 3.2 GiB) and were not touched. Every command pins `--context kind-poc05`.

`deploy/kind/poc05/run.sh up` now does it all from nothing, in the plan's section 8 order: preflight, `create` (gVisor), `smoke`, `admission` (with its canary), `build`, `load`, `seed.sh base`, the platform, the code-runner Sandbox, `seed.sh keys`, the remote Sandbox, the chassis pods, `pods`, then `request` (two requests per lane). New verbs: `seed`, `apply`, `request`, `up`, `test`, `pods`, `down`.

## 1. LiteLLM v1.103.0 as uid 10010, read-only root, no egress

Answer: works with no exception. The image's user is root, but nothing in its start needs root. The image sets `PRISMA_OFFLINE_MODE=true`, `PRISMA_CLI_PATH=/opt/prisma/binaries/node_modules/.bin/prisma`, `PRISMA_CLI_QUERY_ENGINE_TYPE=binary`, and `PRISMA_BINARY_CACHE_DIR=/opt/prisma/binaries`. The engines sit under `/opt/prisma/.cache/prisma/master/<hash>/<platform>/query-engine` (root-owned, world-readable). Our old `PRISMA_BINARY_CACHE_DIR` (`/root/...`) was unreadable (`Permission denied`) and worked only because offline mode bypassed it. Fixed to the image's value. ## 2. Virtual keys on LiteLLM v1.103.0

Answers, from `/key/list?key_alias=svc-echo&return_full_object=true` (master key as a header on curl's stdin) and temporary keys `t19-routes` and `t19-noperm`, deleted afterwards:

- Per-key MCP permissions: `object_permission.mcp_servers` plus `object_permission.mcp_tool_permissions` (`{server: [tool, ...]}`) work as written. The commented fallback (access groups) is not needed. A key with no `object_permission` lists zero tools (`"tools":[]`), so F16's "falls back to all servers" does not happen on this release.
- Tags: `metadata.tags` is stored (`{"tags":["agent:echo"]}`); top-level `tags` stays `null`. Kept `metadata.tags`.
- Delete by alias: `POST /key/delete {"key_aliases": [...]}` returns `{"deleted_keys":[...]}`, and the deleted key then gets 401.
- Allowed routes (F16): the route groups are `LiteLLMRoutes` members. `openai_routes` plus `mcp_inference_routes` let the key chat, list models, and use `/mcp/`. `/key/generate`, `/key/list`, and `/v1/mcp/server` (MCP management) get 403 "Virtual key is not allowed to call this route". `seed.sh` now sets `allowed_routes: ["openai_routes", "mcp_inference_routes"]`; keys re-minted with `seed.sh rekey`. - Refusals with their control, `POST /v1/chat/completions` model `fake-chat`:

## 10. Memory per pod and for the node

Measured 2026-10-08T14:23Z, every pod Ready, after the requests above. The cluster has no Metrics API (`kubectl --context kind-poc05 top pods -A`: "error: Metrics API not available"), so each pod's figures come from its pod cgroup on the node (cgroup v2), read with `docker exec poc05-control-plane`: `memory.current`, working set = `memory.current - inactive_file` (`memory.stat`, the kubelet's definition), `memory.peak`, and `oom_kill` from `memory.events`. The pod cgroup is `/sys/fs/cgroup/kubelet.slice/kubelet-kubepods.slice/kubelet-kubepods-<qos>.slice/kubelet-kubepods-<qos>-pod<uid>.slice`, found by the pod's UID. For a gVisor pod the figure is the whole sandbox (sentry and gofer included). The node is `docker stats` plus the node's root cgroup.

```
for each Running pod (kubectl --context kind-poc05 get pods -A -o json: namespace, name, uid, runtimeClassName, limits):
  dir=$(docker exec poc05-control-plane find /sys/fs/cgroup/kubelet.slice/kubelet-kubepods.slice -maxdepth 2 -type d -name "*-pod${uid//-/_}.slice")
  docker exec poc05-control-plane sh -c "cat $dir/memory.current $dir/memory.peak; awk '\$1==\"inactive_file\"{print \$2}' $dir/memory.stat; awk '\$1==\"oom_kill\"{print \$2}' $dir/memory.events"
docker stats --no-stream --format '{{.Name}} {{.MemUsage}}' poc05-control-plane
```

## Kind tier, 2026-10-08

### The fork test under host load

Two later `test-remote` runs on the same cluster failed (2 failed, 232.58 s; 1 failed, 205.26 s), one of them in `test_process_limit_refuses_forks_past_the_allowance` with `exit_code: -9, timed_out: True`. The run above took 96 s.

Cause: the run is slow, not hung, and the main cause is outside the repository. From about 10:31 a 3D game ran on the Mac at 270 to 335 % CPU (`ps`), and the Mac's load average stayed at 12 to 17. The green runs above were from 10:22 to 10:27, on the same code-runner image (`3e74cac38e30`). Under that load, the code runner (500m CPU, 256Mi) forks slowly under gVisor, and the forked Python children fill its memory:

- Fork timing inside the tool, 64 wanted (printed per fork with `flush`): 26 children at 11.0 s, then the 10 s ceiling killed the call. The 5-child control took 0.4 to 0.9 s.
- The same fork code run directly in the pod with the tool's `RLIMIT_NPROC` and no 10 s ceiling (`kubectl exec ... python -I -`): `{"nproc_limit": 35, "started": 32, "refused": "EAGAIN", "fork_s": 68.14}`. The refusal holds; it took 68 s.
- The pod cgroup on the node during that run: `memory.current` went from 111 MB to 268 MB (the 256Mi limit) after about 15 children and stayed there; `memory.events max` went from 2047 to 2801; `cpu.stat throttled_usec` rose by about 158 s. A forked Python child costs 5 to 8 MiB under gVisor, so 31 of them do not fit next to the server.
- During such runs the code runner's liveness probe (1 s default timeout) failed and the kubelet restarted it: 3 restarts, at least 2 of them during these diagnostics. `pids.current` on the node stayed at 119 to 120 of 256; no process was left between calls (`/proc` in the sandbox showed only the server).

Fix, test only: each child now execs `/bin/cat` on the pipe instead of staying a Python process (`test_poc05_kind_code_runner.py`, `FORKS`). The refusal assertion and the started-count bounds are unchanged. The same direct run then gave `"started": 32, "refused": "EAGAIN", "fork_s": 8.65` (later 9.08 and 10.71), and `memory.current` went from 119 to 129 MB with no new `memory.events max`. No timeout was raised: the 10 s is the tool's own ceiling (`Limits.max_timeout_s`).

The CPU limit is a sandbox value (plan section 2.11); it was not changed.

Findings for platform-security (no probe or limit changed; the security review decides):

1. One caller can restart the code runner for everyone. A fork storm inside one call, still within `RLIMIT_NPROC` (32 children, then EAGAIN), pushes the pod to its 256Mi memory limit (`memory.current` 268 MB, `memory.events max` rising). The server then misses its liveness probe (HTTP `/health`, the default 1 s timeout, `periodSeconds: 10`, `failureThreshold: 3`) and the kubelet restarts it: `Liveness probe failed: ... context deadline exceeded`, then `Container code-runner failed liveness probe, will be restarted`. The code runner restarted 3 times today; at least 2 came from the direct fork runs above. Every call in flight on the gateway fails while it restarts. The process and memory caps held; the probe turned their effect into a restart for all callers.
2. Two calls returned `tool_unavailable: the gateway answered HTTP 400`. The first, at about 10:41:40 local (08:41:40 UTC), was a 64-fork call right after a timed-out one; the code runner's first restart came before 08:42:31 UTC (the new container's `startedAt`). That call fell in the window of the failing probes, so it most likely hit a server that was not answering. The second was the fourth "before the fix" run (10:50:19 to 10:50:56 local), right after run 3's timed-out call. There was no restart around it: `restartCount` was 3 before and after, and the last restart was at about 10:47. LiteLLM's log no longer holds that minute (`run.sh logs` keeps 200 lines). In the lines it does hold, LiteLLM answers `POST /mcp/ HTTP/1.1" 400 Bad Request` to the chassis pods on each refresh, next to a successful tool fetch from `code_runner`. So a 400 at the gateway is not on its own a sign of a down server. The cause of the second 400 is not settled.

Why `agent-echo` crash-looped: probe timeouts under host load, not OOM. From the pod's events (`kubectl --context kind-poc05 -n poc05-agents get events --field-selector involvedObject.name=agent-echo-fb9fb58d7-4nkk9`; the pod itself was replaced by the restart, so `describe` has nothing left to show):

- 08:32:12 UTC (10:32 local, about a minute after the game started): `Liveness probe failed: command timed out: "python -c import urllib.request,sys; ..."` (3 times). The workload's probes are `exec` probes that start a new Python each time, with `timeoutSeconds: 3`. Under the load, starting Python alone took longer than that.
- 08:34:50: `Container workload failed startup probe, will be restarted`. Then 135 startup probe timeouts (the same exec probe), 9 times `Container workload failed liveness probe, will be restarted`, 12 starts, and the 5 m back-off. 780 times `Readiness probe failed: HTTP probe failed with statuscode: 503` on the chassis: its `/ready` reports the workload as down.
- The workload's `lastState` was `Completed`, exit code 0: the kubelet's SIGTERM after a failed probe, then a clean exit. It was not `OOMKilled` (137). The old pod's cgroup went with the pod. The replacement pod's cgroup shows `memory.events` `oom 0`, `oom_kill 0`, `max 0`, and `memory.peak` 246 MB of 512 MiB.
- The replacement pod had the same trouble at its start. The chassis native sidecar was killed twice by its startup probe (`Init container chassis failed startup probe`, `lastState` `Error`/137, the kubelet's SIGKILL), then came up. At 09:12:45 both chassis pods failed `/ready` with `context deadline exceeded`. At 09:15 `kubectl` got `net/http: TLS handshake timeout` from the API server. The Mac's load average was 24.56, with the game at 324 % CPU and an offline `make check` running.

So under this host load every exec probe that starts Python and every 1 s HTTP probe times out, and the kubelet restarts healthy containers. That is the same mechanism as finding 1, from a different source. The verdict runs wait for an idle host.
