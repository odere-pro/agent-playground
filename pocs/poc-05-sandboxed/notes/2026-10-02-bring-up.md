# PoC-5 bring-up on kind (T19, 2026-10-02)

What it took to get the whole PoC-5 stack running on the kind cluster `poc05`, and what only the cluster could settle. Host: macOS arm64, Docker Desktop VM 7.75 GiB, 14 CPUs; the user's `paligo-*` stacks kept running (about 3.2 GiB) and were not touched. Every command pins `--context kind-poc05`.

`deploy/kind/poc05/run.sh up` now does it all from nothing, in the plan's section 8 order: preflight, `create` (gVisor), `smoke`, `admission` (with its canary), `build`, `load`, `seed.sh base`, the platform, the code-runner Sandbox, `seed.sh keys`, the remote Sandbox, the chassis pods, `pods`, then `request` (two requests per lane). New verbs: `seed`, `apply`, `request`, `up`, `test`, `pods`, `down`.

## 1. LiteLLM v1.103.0 as uid 10010, read-only root, no egress

Answer: works with no exception. The image's user is root, but nothing in its start needs root. The image sets `PRISMA_OFFLINE_MODE=true`, `PRISMA_CLI_PATH=/opt/prisma/binaries/node_modules/.bin/prisma`, `PRISMA_CLI_QUERY_ENGINE_TYPE=binary`, and `PRISMA_BINARY_CACHE_DIR=/opt/prisma/binaries`. The engines sit under `/opt/prisma/.cache/prisma/master/<hash>/<platform>/query-engine` (root-owned, world-readable). Our old `PRISMA_BINARY_CACHE_DIR` (`/root/...`) was unreadable (`Permission denied`) and worked only because offline mode bypassed it. Fixed to the image's value. The start ran 184 migrations on an empty database. Its first `migrate deploy` hit `P1001` (Postgres not yet answering) and the retry passed. Nothing was downloaded. The only "download" lines are Prisma's warning that it does not know the `wolfi` distro and falls back to the debian engines. `/tmp/.cache` holds 28K. Pod start to Ready: 50 s (09:51:11 to 09:52:01), 0 restarts.

## 2. Virtual keys on LiteLLM v1.103.0

Answers, from `/key/list?key_alias=svc-echo&return_full_object=true` (master key as a header on curl's stdin) and temporary keys `t19-routes` and `t19-noperm`, deleted afterwards:

- Per-key models, budget, and rpm: `models`, `max_budget`, `budget_duration`, `rpm_limit` are stored as sent.
- Per-key MCP permissions: `object_permission.mcp_servers` plus `object_permission.mcp_tool_permissions` (`{server: [tool, ...]}`) work as written. The commented fallback (access groups) is not needed. A key with no `object_permission` lists zero tools (`"tools":[]`), so F16's "falls back to all servers" does not happen on this release.
- Tags: `metadata.tags` is stored (`{"tags":["agent:echo"]}`); top-level `tags` stays `null`. Kept `metadata.tags`.
- Delete by alias: `POST /key/delete {"key_aliases": [...]}` returns `{"deleted_keys":[...]}`, and the deleted key then gets 401.
- Allowed routes (F16): the route groups are `LiteLLMRoutes` members. `openai_routes` plus `mcp_inference_routes` let the key chat, list models, and use `/mcp/`. `/key/generate`, `/key/list`, and `/v1/mcp/server` (MCP management) get 403 "Virtual key is not allowed to call this route". `seed.sh` now sets `allowed_routes: ["openai_routes", "mcp_inference_routes"]`; keys re-minted with `seed.sh rekey`. (`llm_api_routes` would also work but adds pass-through and agent routes.)
- Refusals with their control, `POST /v1/chat/completions` model `fake-chat`:

```
chat no key        HTTP 401  "Authentication Error, No api key passed in."
chat random key    HTTP 401  "Invalid proxy server token passed. Received API Key = sk-...434e, Key Hash (Token) = ..."
chat chassis key   HTTP 200  {"model":"fake-chat", ... "content":"ok"}
```

Finding (for platform-security): LiteLLM's 401 body echoes the last 4 characters of the refused key and its hash. That is harmless for a random key. For a mistyped real key, it is 4 characters of it. LiteLLM's own logs may carry the same line (verification item 11 should check).

## 3. The MCP gateway

- Header: both `Authorization: Bearer <key>` and `x-litellm-api-key: <key>` work (identical 200 lists). The adapter's default (`Authorization`) is fine; `LITELLM_MCP_AUTH_HEADER` stays unset.
- No key, or an unissued key: HTTP 401 `{"error":"authentication_required","message":"Authenticate with the gateway to use the MCP endpoint."}`.
- Naming: the workload sees `<server>-<tool>`: `fake_tools-glossary_lookup`, `fake_tools-note_write`, `code_runner-run_python`. The result `_meta` carries `litellm.ai/server_outcomes` per server. `unlisted_probe` is absent from the list.
- `readOnlyHint` survives (`true` on glossary_lookup, `false` on note_write and run_python).
- Unlisted tool (`fake_tools-unlisted_probe`): HTTP 200 with an MCP error result, `isError: true`, "Tool 'unlisted_probe' is not allowed for your key/team on server 'fake_tools'". A listed server's tool not on this key (`svc-probe-sidecar` calling run_python): `isError: true`, "User not allowed to call this tool."
- `_meta.idempotency_key` is NOT forwarded. note_write with only `_meta` returned `idempotency_key_required` from the server. With the `idempotency_key` argument, the same key twice returned the first note (`note-1-cb261ff66f00`, text "A" both times), and run_python returned `42`. The chassis adapter already sends both (`chassis/adapters/mcp/gateway.py`), so no code change was needed.
- Through the chassis: a "glossary" request on both lanes makes the workload call `glossary_lookup` via the chassis's `/mcp` and the gateway (see "Requests" below).
