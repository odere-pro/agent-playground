- **055 CH-6, the per-call code sandbox.** The code runner is a dispatcher that claims a fresh gVisor sandbox per call (`SandboxClaim` on the `code-runner` warm pool) and deletes the claim after. Admission holds templates to `Unmanaged` NetworkPolicy, no env injection, and no volume claims, and claims to `warmPoolRef: code-runner`, no `env`, no pod labels or annotations, and `shutdownPolicy: Delete` with `shutdownTime`. Recorded, not fixed: (a) **B4 has one platform exception.** The dispatcher holds a Kubernetes token and the one `ipBlock` in PoC-5, to the API server on TCP 6443; no workload, remote, or sandbox gets either (`deploy/kind/poc05/platform/code-runner-dispatch.yaml`). (b) **Claim deletion is a denial of service.** A stolen dispatcher token can delete other callers' claims, which ends their calls with `sandbox_lost`. It cannot create templates or pools, change a claim, or reach another namespace (`kubectl auth can-i` checks in `test_poc05_kind_admission.py`). Why: the sandbox and admission are this issue's.
- **055 CH-6, `/dev/shm` under gVisor (accepted).** runsc mounts its own tmpfs at `/dev/shm` and ignores the pod's 8Mi `emptyDir`; one call wrote 17 MiB with no error. `platform-security` accepted it on 2026-10-09, owner this issue: with a sandbox per call nothing there reaches the next caller, and the pod's 256Mi memory limit bounds it. Evidence: `test_poc05_kind_code_runner.py::test_dev_shm_is_bounded_by_the_per_call_pod`; `test_dev_shm_is_capped` stays `xfail(strict=True)`, the one xfail in the kind runs (`2026-10-08-remote-suite.md`, "Runs"). `remote-echo` is untested here (blind-spots note). Open: a runsc option that honors the pod's mount (`dev.gvisor.spec.mount.*` is a lead). Why: the sandbox limits are this issue's.
