## To apply

- **055 CH-6**: what PoC-5 built. The `remote` connector with a per-remote bearer token (mTLS is the next step, ADR-005); the remote listener on the pod IP with 401 `remote_unauthenticated` and 403 `run_required`; the remote pod on gVisor through agent-sandbox, with no DNS and one egress edge to 8091; `spec.trust` and the `agent-trust-rule` ValidatingAdmissionPolicy, rules 0 to 8. Open: the admission CEL ran on the server only through the canary and `run.sh admission`, not the kind test; criterion 8 is partly shown (no in-pod probe); the managed-runtime auth adapter and its CI job are not built; criterion 1's kind half is not in CI yet: the remote-lane workflow is manual until the gVisor x86_64 sum and the kind and kubectl sums are pinned and the remote kind test files exist; the "what the chassis cannot control" list is `notes/2026-10-02-blind-spots.md`. Why: PoC-5 is this issue's first build.
- **054 H-16**: `ToolPort` write mode, the idempotency keyword, and the error codes `unknown_tool`, `tool_denied`, `tool_unavailable` (contract v4, "Ports"); `McpGatewayTools` passes the same `ToolPortContract` as the fake (`packages/chassis/tests/test_tool_gateway_contract.py`); tool keys are scoped to agent and request. Findings: the LiteLLM gateway names tools `<server>-<tool>` and does not forward `_meta` (bring-up, item 3). The adapter always sends the idempotency key in `_meta` and adds it as a tool argument only when the tool's schema declares it (`McpGatewayTools.call`, `chassis/adapters/mcp/gateway.py`), so a write tool that does not declare it never gets the key; a third-party tool server may also ignore that key; the code runner's result cache is in memory. Why: the tool port and its real adapter are this issue's.
- **022 H-6**: the uncorrelated cap per replica (`spec.limits.uncorrelated_tokens_per_minute`, 20000, suggested), so N replicas allow N times the limit; LiteLLM's key budget is the cluster-wide cap (contract v4, Known gaps). The remote listener logs method and path only, never the header. Why: rate limits and log hygiene are this issue's.
- **026 CH-4**: hard requirement 1 on kind. LiteLLM with a master key and one virtual key per service, `allowed_routes` limited to `openai_routes` and `mcp_inference_routes`; no `allow_all_keys` in kind or Compose; Valkey with its `default` user off and an ACL user; MinIO key pairs; the fake servers and the code runner closed by NetworkPolicy only (bring-up, items 2, 3, 5). Open: H11 (no broker on kind; with 020 X-8); H01 shown only as a static check, since nothing answers at the metadata address on kind; DNS in the sidecar lane (H20). Why: the chassis-only-credentials rule and egress are this issue's.
- **024 CH-3**: in the PoC-5 sidecar lane the chassis is the native sidecar (an init container with `restartPolicy: Always`) and the workload is the main container (`deploy/kind/poc05/agents/agent-echo.yaml`, header and line 74). This is the reverse of PoC-4's pick. Why: the proxy must bind before the workload starts (H14; contract v4, "Bind order"). Also carry: `podPidsLimit` 256 is a node setting (`deploy/kind/poc05/cluster.yaml`), and under gVisor each guest process costs about three host PIDs (spike, question 6). Why: the chart carries the container roles; the owner must pick one order for both lanes or record two.
- **004 G-2**: a model stream inside a run that the client closes early gives its reservation back to the run uncharged (`_Hold.release` in `packages/chassis/src/chassis/server/model_proxy.py`; PoC-4 debt, handoff). An uncorrelated stream that started is charged. The agent tag is in the virtual key's `metadata.tags` now, but H31 (a spoofed tag) was not run, so the criterion "counted under the agent of its key" stays open. Why: per-run cost counting is this issue's.
- **020 X-8**: H11 is a recorded exception in PoC-5 (`notes/2026-10-02-h11-queue-exception.md`). No broker runs on kind. The PoC-4 Compose Kafka still has no auth. The broker stays behind `EventPort`. A new broker is either a Dapr pub/sub component behind the `dapr` adapter or a broker adapter bound to `EventPortContract`; no chassis change. Result events must not carry caller data on a shared broker until H11 passes. Why: the H11 note names this issue to close it.
- **060 H-23** (exists): a broker added here must pass the whole `EventPortContract` against a real broker with no xfail. `chassis.core` and `chassis.ports.events` import no broker client (`test_poc05_events_agnostic.py`). Why: the queue decision of 2026-10-02 keeps the broker behind the port; this issue adds the brokers.
