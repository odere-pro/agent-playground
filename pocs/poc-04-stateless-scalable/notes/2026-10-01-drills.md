
No request lost. Each of the 7 retried keys, sent again after the kill, returned the same envelope with `Idempotent-Replayed: true`; only pair 1 was alive then, so the replay came from the other replica's view of the shared Valkey state.

First attempt: the same `docker kill` of both containers did not answer within the script's 30 s timeout, and the script crashed with `subprocess.TimeoutExpired` (both containers did exit 137). A second kill took 1.7 s, and a kill of the workload alone 0.35 s, so this is Docker Desktop latency, not the stack. Fix in `load/kill_drill.py`: the Docker call timeout is now `DOCKER_TIMEOUT_S = 90` (suggested) and a timeout is recorded in the report instead of crashing.

## 6. Hung workload: `docker pause` (plan, section 7)

Script: `notes/drills/hung.py`. Two pairs of `echo-python`. `/ready` is read inside `poc04-chassis-N-1` on its own address; calls go through Traefik.

```console
$ deploy/compose/scale.sh up echo-python 2
$ uv run python notes/drills/hung.py
before: chassis-1 /ready -> 200 {"status":"ready"}
before: 40 sequential calls via Traefik -> ok 40, not ok 0, max 7987 ms
$ docker pause poc04-workload-1-1
after 9.7 s: chassis-1 /ready -> 503 {"status":"not ready","reason":"workload_unreachable"}
chassis-2 /ready -> 200 {"status":"ready"}
paused: 40 sequential calls via Traefik -> ok 40, not ok 0, max 368 ms
$ docker unpause poc04-workload-1-1
after 2.0 s: chassis-1 /ready -> 200 {"status":"ready"}
unpaused: 40 sequential calls via Traefik -> ok 40, not ok 0, max 396 ms
```

`/ready` turned 503 `workload_unreachable` 9.7 s after the pause and 200 again 2.0 s after the unpause. With pair 1 hung, 40 of 40 calls succeeded and none took more than 368 ms, so Traefik sent none to the hung pair (a call routed there would hang to the client's 10 s timeout). The routing claim is inferred from latency and success, not from a Traefik log. The 7987 ms maximum before the pause is the first call on a fresh stack.
