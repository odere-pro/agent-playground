# Compose stack: security requirements (PoC-1 `local` and `fake` variants; PoC-2 `sidecar` lane; PoC-4 scale stack; PoC-5 exceptions)

Rules from ADR-001 hard requirement 1 and item 4, `deploy/CLAUDE.md`, and the root hard rules. The developer follows this; the reviewer checks it. Values the epic does not give are marked `suggested:`.

## 1. Who holds which credential

| Credential | Lives in | Set from | Never in |
| ---------- | -------- | -------- | -------- |
| Provider API key (`OPENAI_API_KEY` or similar) | LiteLLM container env only | `.env` (untracked) | `docker-compose.yaml`, `litellm/config.yaml`, chassis env, logs, prompts |
| LiteLLM master key (`LITELLM_MASTER_KEY`) | LiteLLM container env only | `.env` | any other container, any file |
| Chassis key (`LITELLM_API_KEY`) | Chassis container env only | `.env` | LiteLLM config, logs, prompts, the fake model server |

- Commit `deploy/compose/.env.example` with every name and an empty value. `.gitignore` already ignores `.env` and keeps `.env.example`.
- Pass keys by interpolation, one per service: LiteLLM gets `OPENAI_API_KEY=${OPENAI_API_KEY}` and `LITELLM_MASTER_KEY=${LITELLM_MASTER_KEY}`; the chassis gets `LITELLM_API_KEY=${LITELLM_API_KEY}` and `LITELLM_BASE_URL=http://litellm:4000/v1` (plus `CHASSIS_MODEL_URL`, the chassis's own proxy for the in-process workload; not a secret). Do not put `env_file: .env` on the chassis or the fake model server: that would hand them the provider key.
- `litellm/config.yaml` references keys as `api_key: os.environ/OPENAI_API_KEY` and `master_key: os.environ/LITELLM_MASTER_KEY` (suggested: LiteLLM's `os.environ/` syntax). A literal that starts with `sk-` is a defect, except the placeholder `api_key: fake` for the fake model server, which is not a secret.
- **Master key vs. virtual key.** The master key administers LiteLLM; the chassis should call with a scoped virtual key (models, budget, rate limit). LiteLLM issues virtual keys only with a Postgres behind it. For PoC-1 (one consumer, `inprocess` lane, no workload container) do this: **suggested: set `LITELLM_API_KEY` to the master key's value in `.env`, PoC-1 only.** Keep the two names separate so the switch to a real virtual key is a `.env` edit. Record it as debt in `pocs/poc-01-*/notes/`: it fails G-1's criterion "no service config holds the master key". It must be paid by PoC-5 (one scoped key per service is an exit criterion) and it blocks PoC-7 budgets. Not recommended now: the LiteLLM Postgres, because `docker compose up` would then need a key-generation step before the chassis can start, which breaks "no manual steps".
- No secret in any prompt or log: the chassis never puts env values into a prompt, and the fake model server's scripts contain no key.

- **PoC-6 exception (`scripts/poc06_mac.sh`).** The Mac command uses the LiteLLM master key as the chassis key, as PoC-1 does. It is allowed only because all of these hold: it is local, single user, and run by the owner; LiteLLM listens on `127.0.0.1` only; the key is random per run (`sk-poc06-` plus 48 hex characters) and never written to a file, and it reaches a process only as a prefix assignment, never through `export`; LiteLLM has two fixed routes; workloads get no key; and hosted spend is capped on the provider side, so **set a provider budget (a spend limit) before the run**. The provider key is in the LiteLLM container of the `hosted` step only. Debt and the fix (a virtual key per run, owner 026 CH-4): `pocs/poc-06c-pretrained-slm/notes/2026-10-09-mac-command-debt.md`.

## 2. Images and dependencies pinned

- Every `image:` is `name:tag@sha256:<digest>`. Resolve with `docker buildx imagetools inspect ghcr.io/berriai/litellm:<tag>` (or `docker manifest inspect`) and paste the digest. The digest is checked in and bumped on purpose, in its own commit, with the command output in the PR.
- LiteLLM: suggested a release after 1.82.8; 1.82.7 and 1.82.8 were malicious (reuse analysis, watch-outs). Verify the tag against <https://docs.litellm.ai/blog/security-update-march-2026>.
- llama.cpp and Postgres (if ever added) follow the same rule. The chassis and fake model server images are built from this repo; their `FROM` base is pinned by digest too.
- Chassis Python deps come from `uv.lock` only: suggested `uv sync --locked --no-dev` in the Dockerfile, so uv checks the lock's hashes and refuses a drifted resolve. No `pip install <name>` without a hash.

## 3. Network

- One Compose network (the project default is fine). No `network_mode: host` on any service. No `extra_hosts`, no `privileged`, no Docker socket mount.
- Published ports, and only these: chassis `127.0.0.1:8080:8080`; LiteLLM `127.0.0.1:4000:4000` for the demo `curl` and the token log. Fake model server and llama.cpp have no `ports:` at all. Every published port has the `127.0.0.1:` prefix.
- PoC-5 sidecar hostile case (`docs/planning/poc/005-PoC-5-sandboxed.md`, "hostile suite for the `sidecar` lane"): the workload cannot reach LiteLLM on its own. In PoC-1 the workload is in-process, so the case is not yet testable; it becomes live in PoC-2 when the workload container arrives and must get no `LITELLM_API_KEY`.

## 4. Offline variant

- Two files: `docker-compose.yaml` is the `fake` profile and the default. `docker-compose.local.yaml` is the `local` override (`docker compose -f docker-compose.yaml -f docker-compose.local.yaml up`). suggested: the offline stack is the default so a bare `docker compose up` needs no key.
- `fake`: LiteLLM loads `litellm/config.yaml`, where `big-default` and `local-small` both point at `http://fake-model-server:8081/v1` with `api_key: fake`. llama.cpp is not started. It must start with an empty `.env` and no internet.
- `local`: LiteLLM loads `litellm/config.local.yaml`; `big-default` is the API model, `local-small` is llama.cpp at `http://llama-cpp:8080/v1`.

## 5. Tags, logging, health

- Tags: every model call from the chassis carries `metadata.tags: ["agent:<name>"]` and the same in the `x-litellm-tags` header (suggested; per LiteLLM tag-based cost tracking). The route is the `model` field, so it needs no tag. suggested: `litellm_settings.enable_tag_budgets: true` is not needed in PoC-1; do not set it. Debt for G-2: the agent tag comes from the request, so it is spoofable until the virtual key carries it.
- Logging: `litellm_settings.turn_off_message_logging: true` (suggested), so LiteLLM keeps token counts but not request or response content. `set_verbose` and `--detailed_debug` stay off. The chassis adapter logs route, tokens, and status; never the `Authorization` header, never `LITELLM_API_KEY`.
- Cost map: `LITELLM_LOCAL_MODEL_COST_MAP: "True"` on the LiteLLM service, so it uses the map bundled in the pinned image and downloads none at run time.
- Health: LiteLLM `healthcheck` hits `/health/liveliness` (no key needed); the chassis `healthcheck` hits `/health`. The chassis has `depends_on: litellm: condition: service_healthy`; LiteLLM in `fake` depends on the fake model server the same way. suggested: use `python -c "import urllib.request,sys; ..."` for the LiteLLM check, because `curl` may be absent in the image; verify.

## 6. Sidecar lane: the shared network namespace (PoC-2)

`docker-compose.sidecar.yaml` runs one workload container next to the chassis, with `network_mode: "service:chassis"`. Rules from ADR-001 (hard requirement 1, decision items 3, 4, and 6; Consequences, "The workload shares the pod's network") and `deploy/CLAUDE.md`.

- **Why the shared namespace is acceptable here.** It is the Compose form of two containers in one pod. The workload's A2A server binds `127.0.0.1:9000`, so only the chassis reaches it; it publishes no port and joins no network of its own. The chassis's public port binds the container's own address (from `socket.gethostbyname(socket.gethostname())`), not `0.0.0.0`, so the loopback carries only the sidecar and the chassis's proxies on `127.0.0.1:8090` (`/v1` for models, `/mcp` for tools), which stay on their loopback default.
- **The workload holds no key.** Its env is exactly `CHASSIS_MODEL_URL`, `CHASSIS_TOOL_URL`, `HOST`, and `PORT`. No `env_file`, no variable whose name matches `KEY`, `TOKEN`, `SECRET`, or `PASSWORD` (any case), no Docker socket, no `privileged`. The chassis stays the only service with `LITELLM_API_KEY`, and the overlay adds no key and no port to it. The demo prints the key-like variable names in each workload container (`env | cut -d= -f1 | grep -i -E 'key|token|secret'`, names only, so a defect never writes a value into a record) and expects none. It allow-lists one name, `GPG_KEY`: the official python base image sets it to the id of the CPython release signing key, which is public and not a credential.
- **The workload container is hardened.** Every workload service has `cap_drop: [ALL]`, `security_opt: ["no-new-privileges:true"]`, `read_only: true` with `tmpfs: [/tmp]`, and `user: "10002:10002"`, the non-root user and group every workload image creates (the uid table in `deploy/README.md`). `test_compose_sidecar.py` checks all four and that the uid matches each Dockerfile; `packages/chassis/tests/test_image_uids.py` checks every image and manifest.
- **What the namespace does not stop.** The workload can reach every address the chassis can: `litellm:4000`, `fake-model-server:8081`, `llama-cpp:8080` in the `local` variant, the chassis's public port on its container address, and whatever egress Docker allows. ADR-001 accepts this only where every internal service needs a credential the chassis holds, and today not every one does:
  - `fake` variant: LiteLLM runs open (published on the host's loopback only, but open to every service on the Compose network; the note in `litellm/config.yaml`), so a workload can call it with no key. Accepted for the fake variant only: it fronts a scripted fake, costs nothing, and holds no credential.
  - `local` variant: LiteLLM has auth on, so a direct call without a key gets 401. But the model servers behind it do not: `llama-cpp` serves `:8080` with no key, and the fake model server still serves `:8081`. So a sidecar workload in the shared namespace can call a real model (`http://llama-cpp:8080/v1`) directly, bypassing the chassis's count, trace, and budget. This is open, not accepted.
  - The workload also shares the chassis's ports. Until PoC-5 the chassis's entrypoint waited up to 120 s for the sidecar before `chassis serve` bound `127.0.0.1:8090`, so in that window a workload could bind the proxy port itself. Fixed in PoC-5 (H14): the proxies bind first, and the wait moved to readiness (`--startup-wait-s`).
  - These are PoC-5 hostile-suite cases for the `sidecar` lane, next to "the workload cannot reach LiteLLM on its own": "the workload cannot reach a model server directly" and "the workload cannot bind the chassis's ports". None may carry over to a variant with a real model past PoC-5.
  - suggested: give `llama-cpp` a key the chassis side holds. Upstream `llama-server` documents `--api-key` (env `LLAMA_API_KEY`); the wiring would be `LLAMA_API_KEY` on `llama-cpp` and `litellm` only, in `docker-compose.local.yaml`, `api_key: os.environ/LLAMA_API_KEY` in `litellm/config.local.yaml`, and the name in `.env.example`. Not wired yet: the flag is not verified against the pinned image `server-b11243` (verify with `docker run --rm <image> --help | grep -A1 api-key`). It does not close the fake model server, which has no auth at all; that needs the egress rule in PoC-5.
- **The workload trusts the chassis's proxies, and the proxies trust the namespace.** Anything in the namespace can call `127.0.0.1:8090` with no credential, and the chassis spends its own key on that call. The proxies count, trace, and apply per-run budgets keyed by `traceparent` (ADR-001 item 6). A call with no trace id, or one that names no in-flight run, has no run budget. It is served and counted (`chassis.model_calls_uncorrelated`) and logged. Since PoC-5 (H16) a per-replica token bucket caps it: `spec.limits.uncorrelated_tokens_per_minute` (suggested 20000), 429 `budget_exhausted` past it. N replicas allow N times the cap; the LiteLLM key's budget is the cluster-wide cap. The workload, in turn, takes what the proxies answer as the model's and the tool's answer. That is why the `sidecar` lane is for trusted workloads only (ADR-001 item 5); untrusted code goes `remote`.
- **Start order without a restart policy.** The workload needs the chassis's namespace, so the chassis container starts first. `chassis serve` binds its proxies at once (PoC-5, H14); `/ready` stays 503 `starting` while it retries the sidecar's agent card on `127.0.0.1:9000` (`--startup-wait-s`, suggested 120 s); the sidecar connector's `RuntimeError` names the url if the card never came. No `restart:` on any service: a restarted chassis gets a new namespace and the workload stays on the old one, cut off. To swap the workload, remove it and recreate both (`demo-sidecar.sh`).
- **What Kubernetes does instead (ADR-001).** The chassis and the workload are two containers in one pod (a native sidecar, stable since v1.33), so they share localhost the same way, but not file systems, processes, or secrets. What Compose cannot give, the pod adds: a default-deny egress NetworkPolicy per pod that allows only what the chassis needs, with the cloud metadata service and the Kubernetes API in the deny list; `automountServiceAccountToken: false`, or the token projected into the chassis container only; a scoped LiteLLM virtual key per service; and the public port on the pod IP. A Compose network has open egress, and `internal: true` would also block the published port and the provider call, so egress is not enforced here. It is checked in kind in PoC-5.
- **Base images.** The echo-typescript image pins `node:24-slim` by digest (resolved 2026-10-01). The three Python workload images (echo-python, echo-pydanticai, echo-langgraph) reuse the chassis's python and uv digests.
- **Run live on 2026-10-01.** `demo-sidecar.sh` (fake variant) started all four hardened workloads and exited 0: `pocs/poc-02-two-engines-one-contract/demo/2026-10-01-demo-sidecar.md`. The `--local` variant has not run; it needs a provider key in `.env`.

## 7. Scale stack (PoC-4)

`docker-compose.scale.yaml` (project `poc04`) runs 1, 2, or 4 chassis and workload pairs behind Traefik, with Valkey, MinIO, the fake model server, and Kafka in the `events` profile. `docker-compose.scale-dapr.yaml` adds a daprd sidecar to each pair. Design: `docs/plans/2026-10-01-poc-04-stateless-scalable.md`, section 8a.

- **Its own project.** `name: poc04`, network `poc04`. `scale.sh` is the one entry point and passes `-p poc04 -f docker-compose.scale.yaml` on every Compose command. `down` removes project `poc04` only. Nothing prunes, and nothing names a container of another project.
- **Secrets are generated, never written in a tracked file.** `scale.sh` makes `VALKEY_PASSWORD`, `MINIO_ROOT_PASSWORD`, the chassis's MinIO key pair (`CHASSIS_S3_ACCESS_KEY`, `CHASSIS_S3_SECRET_KEY`), `DAPR_API_TOKEN`, and `APP_API_TOKEN` with `openssl rand -hex 24` into `deploy/compose/.env.poc04` (mode 600, git-ignored by `.env.*`). Compose reads that file with `--env-file`, so the PoC-1 `.env` with the LiteLLM key is never read by this stack. Every secret in the Compose files is `${NAME:?set by scale.sh}`: a run without it fails instead of starting with a blank one. `down` deletes the file.
- **Who holds what.** The chassis gets the Valkey password, its own MinIO key pair, and in the Dapr variant the two Dapr tokens. Valkey gets its password, MinIO its root password, `minio-init` the root password and the chassis's key pair (to create that user), and daprd the two Dapr tokens. No workload gets any of them: its env is the four PoC-2 variables plus `DRAIN_TIMEOUT_MS`. The chassis calls the fake model server directly and holds no model key in this stack.
- **The chassis's MinIO user is read-only.** `minio-init` creates it with a policy on the `agent-configs` bucket only: `GetObject`, `GetObjectVersion`, `ListBucket`, `ListBucketVersions`, `GetBucketLocation`. The chassis cannot write its own config.
- **Read-only roots** (exit criterion 5). Every chassis, workload, and daprd container, and Valkey, MinIO, `minio-init`, Traefik, and the fake model server: `read_only: true`, a tmpfs on `/tmp` (MinIO also on `/data`; its data is seeded on every `up`), `cap_drop: [ALL]`, `no-new-privileges`, and a non-root user (`10001:10001` for the chassis, MinIO, and `mc`; `10002:10002` for the workloads; the fake model server's image user `10004`; `999:1000` for Valkey; `65534:65534` for Traefik; daprd's image user `65532`). Kafka is the exception: its image writes its config and log directories at start, so it has no read-only root; it still drops every capability.
- **One published port.** Traefik on `127.0.0.1:18080`, nothing else. Traefik listens on 8000 inside the container (suggested: so it runs as nobody with no capability; port 80 would need `NET_BIND_SERVICE`). It uses the file provider only (`traefik/poc04.yaml`), with no Docker socket, no dashboard, and no API. Valkey, MinIO, Kafka, daprd, the chassis, and the workloads publish nothing.
- **The shared namespace, as in section 6.** Each `workload-N` and `daprd-N` has `network_mode: service:chassis-N`. The chassis serves its public port on the container address; the proxies, the workload (`127.0.0.1:9000`), and daprd (`--dapr-listen-addresses 127.0.0.1`, port 3500) stay on loopback. daprd calls the chassis back on the proxy port 8090, never the public one. No restart policy, for the reason in section 6.
- **Dapr's HTTP and gRPC API is closed to the workload by tokens, not by the namespace; two daprd ports are not.** daprd listens on the pair's loopback, which the workload shares. `DAPR_API_TOKEN` guards daprd's API; `APP_API_TOKEN` guards the chassis's `/dapr/*` routes against a caller that is not daprd. Measured in P18: every non-health endpoint without the token is 401. Not closed: daprd's metrics port 9090 and its internal gRPC port (a random port, mTLS off, no Sentry) listen on every interface with no auth, reachable from the pair's workload and from every container on `poc04` (`pocs/poc-04-stateless-scalable/notes/2026-10-01-dapr-vs-broker.md`). Not tested, but likely: a sidecar-to-sidecar call to that port is forwarded to that pair's `127.0.0.1:8090` with the app token, so it can post events and reach that pair's model and tool proxies. Accepted for the comparison only. If Dapr is kept (ADR-004): Sentry mTLS with access control, or a pinned internal gRPC port bound to 127.0.0.1, and `--enable-metrics=false`.
- **Known gaps, accepted for the PoC only.**
  - Kafka's listener is PLAINTEXT with no auth. Every container on the `poc04` network can publish and consume directly, a workload included, which bypasses the chassis and Dapr's tokens. On kind, the PoC-5 close runs Kafka with SASL/SCRAM and no PLAINTEXT listener (H11, section 8). The Compose stack is still PLAINTEXT. What is left (topic ACLs per service, TLS, the controller listener) is 020 X-8.
  - The fake model server has no auth, as in section 6. A workload can call it directly.
  - Valkey's password is on `valkey-server`'s command line, so it shows in that container's process list and in `docker inspect`. The healthcheck passes it as `REDISCLI_AUTH`, not as an argument. The same holds for `mc admin user add` in the one-shot `minio-init`.
  - Compose has open egress, as in section 6. The egress rule is checked in kind in PoC-5.
  - Result events (`result_events: true`) carry the run's `input` and `output`. The idempotency key is published only as its sha256 hex, in `data` and in the `idempotencykey` and `partitionkey` extensions (fixed 2026-10-01 after this review; `packages/chassis/tests/test_result_events.py` checks the raw key appears nowhere). With the PLAINTEXT broker, any container on `poc04`, a workload included, reads every caller's input and output. Before production: broker ACLs (020 X-8), and `input` opt-in (019 H-17).
  - The idempotency cache stores the request, the events, and the response of a keyed run in Valkey in the clear, for `spec.idempotency.ttl_s` (default 86400 s, reloadable, no ceiling), over `valkey://` with no TLS. Valkey keeps nothing on disk. Before production: TLS, a ceiling on `ttl_s`, and a retention decision (018 H-18).
  - Any caller can fill Valkey: it runs `--maxmemory 256mb` with `noeviction`, every keyed call with a new key adds an entry of up to `max_entry_bytes` (1 MiB) for 24 h, and there is no per-caller quota. Once full, every keyed call is 503 `state_unavailable` until entries expire (measured in the kind drill at about 186k small calls). Unkeyed calls are not affected. Before production: a per-caller quota (PoC-8, 022 H-6), lower defaults (suggested: `ttl_s` 3600, `max_entry_bytes` 65536), and a memory alert.
  - Idempotency is per agent, not per caller: the interfaces have no auth yet (PoC-8). A caller who knows or guesses another caller's key can hold it (the other caller gets 422 for 24 h), learn that it exists, or, with the same input, get the cached answer with the first caller's `request_id` and `trace_id`. When auth arrives, the store key and the fingerprint must include the principal.
  - A store config document can raise `spec.limits` and `spec.idempotency.ttl_s` with no ceiling and change `spec.model.route` and `spec.prompt` at run time. Only MinIO's root user can write the bucket (MinIO, `minio-init`, and `.env.poc04` on the host); the chassis's user is read-only; bucket versioning keeps every change. The hard limit stays the LiteLLM key's budget (ADR-001, item 5).
  - Kafka's controller listener (9093) also binds every interface, topics are created automatically, and its root is writable, so any container on `poc04` can create topics and fill its disk (020 X-8).
- **MinIO image.** MinIO stopped publishing images: `minio/minio`, `minio/mc`, and `quay.io/minio/*` were not pullable on 2026-10-01 (`pull access denied` and 401). The stack uses the community build `pgsty/minio` and `pgsty/mc`, pinned by digest. suggested: `platform-security` decides between this fork, a build from MinIO's source, or another S3 server before anything past PoC-4 uses it.
- **MinIO image decision (platform-security, 2026-10-01).** `pgsty/minio` and `pgsty/mc` are accepted for PoC-4 only, pinned by digest. Before PoC-5 or the `cloud` profile uses an S3 store: MinIO built from source in our registry and signed, or the cloud's S3 in `cloud` (024 CH-3).
- **Images** pinned by digest, resolved on 2026-10-01 with `docker buildx imagetools inspect`: `valkey/valkey:8.1.4-alpine`, `pgsty/minio:RELEASE.2026-08-04T00-00-00Z`, `pgsty/mc:RELEASE.2026-09-16T00-00-00Z`, `apache/kafka:4.1.0`, `traefik:v3.5.3`, `daprio/daprd:1.16.0`. The chassis, the fake model server, and the four workloads are built with the tag `poc04` (`scale.sh build`).

## 8. Exceptions recorded by PoC-5 (plan section 2.12)

PoC-5 checks hard requirement 1 on kind (`docs/plans/2026-10-02-poc-05-sandboxed.md`, section 2.12). These items stay open. Each has an owner.

- **The Compose `local` variant: `llama-cpp` with no key (H09).** On kind the fake model server takes ingress from LiteLLM only, so H09 is fixed there. The Compose `local` variant keeps `llama-cpp` on `:8080` with no key, and a sidecar workload can call it (section 6). Exception, owner `platform-security`. Compose is never the boundary for untrusted code; untrusted code runs only in the kind `remote` lane.
- **The MinIO image.** PoC-5 on kind uses the same `pgsty/minio` and `pgsty/mc` images as section 7, pinned by digest. They are unsigned community builds. Fake data only. Exception, owner `platform-security`: build MinIO from source in our registry and sign it before any real data, or use the cloud's S3 in `cloud` (024 CH-3).
- **Kafka.** On kind, the PoC-5 close runs Kafka with SASL/SCRAM and no PLAINTEXT listener, so H11 is refused without credentials. The Compose scale stack (section 7) is still PLAINTEXT with no auth. Topic ACLs per service, TLS, and the controller listener are 020 X-8.
- **B12, per-caller scope of cached results.** Not closed. Idempotency entries and tool keys are scoped to the agent and the request, not the caller (section 7, "Known gaps"). It is PoC-8 work. For the code runner only, PoC-5 closes it with a fresh sandbox per call. No test claims B12 closed.

## Review checklist

1. Provider key and master key appear only in `.env` and only in LiteLLM's env? Y/N
