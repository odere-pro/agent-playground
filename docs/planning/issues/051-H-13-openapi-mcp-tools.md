## Why

The epic requires an OpenAPI 3.1 spec for every API, with MCP tools generated from it, so REST and MCP never drift apart. The registry, the platform MCP server, and the documentation pack all read this spec or the `/manifest` built from it. Under [ADR-001](../adr/001-chassis-delivery-model.md), the chassis owns the public port, so the chassis builds the spec, not the workload. It is on the longest chain in the backlog, so it comes early in the chassis completion wave, right after service operations (050 CH-5).

## What

- An OpenAPI 3.1 spec generated by the chassis from its own endpoints plus the service's declared operations (050 CH-5). It covers every endpoint, the envelope, and the agent's own input and output JSON Schemas. The workload serves no public API, so it has nothing to add.
- The chassis serves the spec (suggested: `GET /openapi.json`), and CI saves it as a build artifact.
- An MCP adapter in the chassis, built with the MCP Python SDK. It generates MCP tools from the same spec and runs them through the same pipeline and engine connector.
- The `interface.mcp` config flag switches it on or off.
- MCP calls pass the same pipeline stages as REST: auth and scopes, limits, idempotency, and telemetry.
- `GET /manifest`: the registry manifest, built from the agent config (name, version, class, kind, task, interfaces, scopes, events, governance block) plus the OpenAPI spec. It also reports:
  - the chassis version;
  - the lane (`spec.engine.connector`);
  - the trust value (`spec.trust`);
  - the workload and chassis image digests.
- Status after PoC-3: the OpenAPI 3.1 spec, `GET /manifest` v0 (`schemas/manifest.v0.json`), and the agent as one MCP tool at `/v1/mcp`, complete only, generated by `FastMCP.from_openapi` from the `/v1/run` operation, switched by `spec.interfaces.mcp`. The MCP decisions are proposed in [ADR-003](../adr/003-chat-formats-onto-the-canonical-request.md) (item 6) and written in [contract v2](../../contracts/contract-v2.md). The MCP inner call to `/v1/run` forwards only `traceparent`, `tracestate`, and `Idempotency-Key`, and passes the same `spec.limits` checks as REST. Built with FastMCP 4, not the MCP Python SDK directly. LiteLLM's MCP gateway sits in front of `/v1/mcp` in the Compose demo (`deploy/compose/litellm/config.yaml`, fake variant, `allow_all_keys: true`); the per-key grant is 026 CH-4's. Still open: service operations, trust, image digests, scopes, governance, and auth on MCP calls; a run with `status: error` is a normal tool result, not `isError`. See [the PoC-3 debt note](../../../pocs/poc-03-one-interface-every-client/notes/2026-10-01-debt.md).

## Reuse

- **Use:** FastMCP 4. `FastMCP.from_fastapi()` (or its OpenAPI provider) turns the OpenAPI spec into MCP tools, mounted in FastAPI with `http_app()`.
- **Build:** curated route maps (which operations become tools), and `/manifest` built from config plus the OpenAPI spec. The spec includes the service's declared operations (050 CH-5), and `/manifest` reports the chassis version, the lane, and the trust value.
- **Watch:** FastMCP 4 broke the 3.x APIs, so pin it. Do not use fastapi-mcp (no release since 2025-07).
- Details: [reuse analysis](../poc/010-reuse-analysis.md)

## Out of scope

- The AsyncAPI spec (052 H-21).
- Reading `/manifest` into the registry (076 R-1, 083 R-2).
- The platform MCP server (094 P-1).
- The public A2A endpoint and its agent card (061 H-5).

## Acceptance criteria

- [ ] The echo agent and the simplifier publish specs that pass OpenAPI 3.1 validation in CI.
- [ ] An MCP client lists the simplifier's tools with `tools/list`, and a tool call gives the same output as `POST /v1/run`.
- [ ] A contract test fails if an MCP tool's input schema differs from the matching OpenAPI request schema.
- [ ] MCP calls without the right scope are refused, and MCP calls appear in traces.
- [ ] `GET /manifest` returns the config fields, including the governance block, and changes when the config version changes.
- [ ] `GET /manifest` reports the chassis version, the lane, the trust value, and the workload and chassis image digests, and the digests match the running containers.
- [ ] The spec lists the service's declared operations, and a declared operation's MCP tool gives the same output as its REST route.
- [ ] Phase 0 done-when: the echo agent answers through the native, OpenAI, Anthropic, and MCP APIs and through events, streaming and complete where the API supports it, locally and in Kubernetes. It runs in the `sidecar` lane in Kubernetes and `inprocess` in tests. It appears in traces and passes contract tests for each API.
