## Why

Without SLOs, nobody knows when an agent is failing its users. SLOs and alerts turn the per-agent dashboards into signals that reach a person. This issue delivers the Phase 8 done-when part "alerts fire on SLO breaches", and the product plan's phase E record: one week of real SLO numbers. It comes before the incident flow and the runbooks, which start from these alerts.

## What

- SLOs for every agent: availability, p95 latency, and error rate, plus fallback rate for agents with a fallback route (target < 10%, from the success metrics).
- Default targets in the library chart (024 CH-3), overridable per agent (suggested: an `slo` block in the agent config, added to the schema).
- Prometheus recording and alert rules per agent, generated on deploy (suggested: burn-rate alerts on the error budget).
- Every alert carries the chassis version as a label, from a `chassis_build_info` metric, so a fault can be tied to a chassis release. No such metric exists today.
- An alert on the gate's fail-open rate (`chassis.gate_failed_open` over `chassis.gate_runs`) and on a rate-limit store outage. Both outages fail open by design, decided 2026-11-06 (P-1, P-2), so an alert is the only signal.
- Alert routing to on-call (suggested: Alertmanager, part of the Prometheus stack).
- Each alert's `runbook_url` links to `docs/guides/poc-05-runbooks.md` as it stands, until 119 X-6 adds a runbook per alert.
- SLO panels and remaining error budget on each agent's Grafana dashboard and on the container dashboard (046 A-5), generated by `python -m chassis.dashboards`.
- The same rules on the Compose stack (`deploy/compose/poc08`) and on kind.
- Built inputs today: the gate's run and fallback counters and the fallback panel (`packages/chassis/tests/test_metrics.py::test_gated_runs_and_fallbacks_are_both_counted`), and seven generated panels, none of them an SLO or budget panel (`packages/chassis/tests/test_dashboards.py::test_every_panel_names_a_metric_the_chassis_exports`). No rule file, Alertmanager, or `slo` key exists. Proving tests (suggested): `test_a_fallback_rate_above_ten_percent_fires_the_alert`, a Compose drill, and the dashboard generator test over an SLO panel set.

## Out of scope

- Incident events and the serious-incident runbook (118 C-7).
- Runbooks for each alert (119 X-6).
- Load tests (122 X-5).
- Alerts for parts that do not exist yet (broker lag, dead letters, Temporal runs, release rings, the minimum chassis version, the `remote` endpoint) join these rules when 019 H-17, 053 H-22, 100 O-2, and 056 CH-7 ship.
- The same rules in the cloud, when the first cloud (038 X-1a) lands.

## Acceptance criteria

- [ ] A newly deployed agent gets SLO rules (availability, p95, error rate, fallback rate) generated from an `slo` block with chart defaults, no manual step.
- [ ] A fault test on the Compose stack (`deploy/compose/poc08`, a fake agent returning errors) fires the burn-rate error alert and it reaches the Alertmanager receiver (Phase 8 done-when).
- [ ] A latency fault test on the Compose stack fires the p95 latency alert.
- [ ] A gate fallback rate above 10% fires an alert.
- [ ] An alert carries the chassis version from a `chassis_build_info` metric.
- [ ] Each agent dashboard and the container dashboard show each SLO target and the remaining error budget.
- [ ] One week of real SLO numbers is recorded in a weekly note (`record-measurement`) next to the north star.
- [ ] An alert fires on `gate_failed_open / gate_runs` above suggested: 1% over 15 minutes.
- [ ] An alert fires when the rate-limit store is unavailable.
