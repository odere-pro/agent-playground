# Sidecar DNS egress gap (H20), five options, 2026-11-16

Writer: `chassis-architect`, reviewed by `platform-security`. Read against `main` at `71db2e8`. A note for the user's decision, not a decision. No `deploy/` or code change. Values the epic does not give are marked `suggested:`. Facts from upstream docs that no kind run has checked are marked as such.

## Recommendation

Take option 1, wired by the pod half of option 2. Add a platform-owned resolver that answers only cluster names and never forwards. Point agent pods at it with `dnsPolicy: None`, and move the chart's DNS peer to it. That closes the box's DNS item (026 CH-4 line 62, H20) in both lanes. Until it ships, run under option 3 (today's state), with option 4's risk text recorded.

## The gap

- The box, 026 CH-4 line 62: "With `agent-lib`'s NetworkPolicy on a CNI that enforces it, these all fail from the workload container: any public address, any other service's pod, the cloud metadata service, the Kubernetes API, a DNS lookup used to leave the cluster (H20), and the chassis's public port on localhost."
- The evidence: `pocs/poc-09-agent-mvp-template/notes/2026-11-16-026-ch4-kind-poc05.md:440-444`. From `agent-echo`'s workload (`deploy/kind/poc05/agents/agent-echo.yaml`, under `deploy/kind/poc05/agents/network-policy.yaml:43-54`, whose kube-dns rule has the same shape as `_networkpolicy.tpl:56-67`), kube-dns answered `example.com` (rcode 0, two answers). A query sent straight to 1.1.1.1 timed out. It was a probe by hand, not a test. No `agent-lib` render was probed.
- The cause: `agent-lib` lets the chassis pod reach kube-dns on port 53 in every lane (`deploy/helm/agent-lib/templates/_networkpolicy.tpl:56-67`; defaults `_values.tpl:99-102`). A policy cannot tell the two containers apart (`_networkpolicy.tpl:11-13`; ADR-001 line 205). CoreDNS forwards any name out of the cluster (`deploy/kind/poc04/base/network-policy.yaml:45-47`).
- The `remote` lane is closed. It has no DNS rule (`_networkpolicy.tpl:18-19`), and `test_h20_remote_has_no_dns` (`pocs/poc-05-sandboxed/tests/test_poc05_kind_remote_controls.py:427`) passed (`pocs/poc-05-sandboxed/notes/2026-10-08-remote-suite.md:18`; ADR-005 line 106).
- Where H20 is recorded: the threat model (`pocs/poc-05-sandboxed/notes/2026-10-02-threat-model.md:85`, `:101`, `:115`), the blind spots note (`2026-10-02-blind-spots.md:37`, `:55`), the security review (`2026-10-02-review-security.md:170`), `docs/guides/poc-05-how-it-works.md:314`, `:509`, and the backlog review (`docs/reviews/2026-11-06-backlog-review/findings-W2b-chassis-security-deploy.md:23`, `:90`).

## What the rules say

- ADR-001 hard requirement 1 (line 21): "Each pod may send traffic only to what its chassis needs." The chassis's peers are named by labels, with no `ipBlock` (026 line 27), so it never connects outside. Forwarding outside names gives the pod more than it needs. ADR-001 does not say "cluster names only". This is our reading. The literal anchor is 026 line 62.
- ADR-001 item 6 (line 108): "Network policy denies egress by default for every workload pod." Forwarding through kube-dns is egress the policy cannot see.
- ADR-001 item 11 (line 113): the hard requirements are release gates.
- ADR-001 item 5 (line 105): prompt injection does not make an agent untrusted, because "a hijacked agent still reaches models and tools only through its scoped key and the gateway allow-lists."
- What can leak is run data, never credentials. Credentials sit in the chassis container only (026 line 25; ADR-005 line 89, rule 6c). The containers share no processes or files (threat model H26).

What an attacker in the sidecar workload can still do under 3 or 4. They put data in the labels of a name under a domain whose name server they run, for example `<data>.x.attacker.example`. kube-dns forwards it, and their server logs it. TXT answers carry commands back, so the channel goes both ways. DNS caps a label at 63 bytes and a name at 253. No platform budget, trace, or log sees it (blind spots `:29`, `:37`). They cannot open TCP out (1.1.1.1 timed out, the 2026-11-16 note line 442), and cannot read the chassis's credentials. They can also map every service name in the cluster: reconnaissance, not a way out. In the vault's words (`sdlc-vault/wiki/security/Threat model.md`, "Lethal trifecta"), a sidecar agent holds legs A (untrusted content) and B (run data), and DNS is a leg C that no egress allowlist covers (`Prompt injection.md`, the egress allowlist rows). Options 3 and 4 are one choice: 3 is the policy, 4 is its risk record.

Two shapes of option 1 fail in `sidecar`. A DNS sidecar in the pod needs its own egress to kube-dns, which the workload shares, so the workload goes around it. Node-local DNS listens on a link-local node address, which needs an `ipBlock` the chart forbids (026 line 27), and has no per-pod allow list.

## Why option 1

- Hard requirement 1 is a release gate. Option 3 needs an exception to the 026 CH-4 box and, by our reading, to hard requirement 1.
- Item 5's prompt-injection sentence speaks only of models and tools. Its conclusion, that injection does not move the trust line, rests on DNS being closed. A trusted agent that fetches URLs leaks the host name in its lookup, even though the TCP connection then fails.
- The cost is one shared service and a small chart change. No wire contract changes.
