# The story so far

The PoCs build one chassis, one layer at a time. Each review session fills only its own heading. A paragraph says, in at most five plain sentences: what the PoC added, what it builds on, what it hands to the next PoC, and which rule it set that later PoCs must keep.

## PoC-0: scaffold and harness (R0)

PoC-0 set up the uv workspace, the four day-0 ports with their fakes and contract suites, the fake model server, the `fake`/`local`/`cloud` profiles, and the import-lint rule. It also set up the gates (`make quick`, `make check`, harness-lint) and CI, with every action pinned by SHA. It set the rules every later PoC must keep: tests run offline with no keys, every external dependency sits behind a port whose fake passes the same suite as the real adapter, and only the chassis holds credentials. It also set up the agents, skills, and `pocs/` folder shape (README checklist, CLAUDE.md, tests, demo, notes) that every iteration follows. It hands PoC-1 a chassis that resolves only the `fake` profile and passes `make test` offline, ready for the walking skeleton.

## PoC-1: walking skeleton (R1)

PoC-1 added the chassis core: the envelope, the versioned events, `handle`, four ports with in-memory fakes, one contract suite per port, `chassis serve`, and the first real `ModelPort` (LiteLLM). It builds on PoC-0's monorepo, make targets, and offline test gate, and proves one request runs end to end through the chassis and the router, streaming and complete, with tokens counted. It hands PoC-2 the in-memory A2A lane, the event-to-A2A mapping, contract v0, and the fake model server that later engines are tested against. The rule it set: every dependency sits behind a port, and the fake and every real adapter pass the same contract suite, picked by config and never in code. Later PoCs must also keep `make test` offline with no keys.

## PoC-2: two engines, one contract (R2)

PoC-2 added the `sidecar` lane: the workload runs in its own container and serves `handle` over A2A on localhost, through the `workload_a2a` template server. Four engines pass one contract suite behind it: plain Python, PydanticAI, LangGraph, and a TypeScript twin. It builds on PoC-1's in-memory A2A lane, event mapping, and fake model server, and adds a localhost model proxy and MCP tool endpoint that tie each call to its run by `traceparent`. It hands PoC-3 one event stream that looks the same for every engine, contract v1, and `poc02_harness.py`, which every later PoC imports. Later PoCs must keep its rules: no framework import in the chassis, no key in any workload, and every lane passes one suite on localhost and in memory.

## PoC-3: one interface, every client (R3)

PoC-3 put the OpenAI, Anthropic, and MCP interfaces on the public port, beside native `/v1/run`. Each one maps its format onto the one canonical request and back through the shared `serve()` path. It builds on PoC-2's `handle` contract, its engines, and its two lanes, and the interface contract suite runs every interface on every engine in both lanes. It hands PoC-4 one front door, where idempotency and client disconnect could be added once for every interface. The rule later PoCs must keep: a client format is only an inbound adapter onto the canonical request, it passes the same contract suites, and its errors send `public_message(code)`, never the run's own text.

## PoC-4: stateless and scalable (R4)

PoC-4 made a chassis replica disposable: `StatePort` (Valkey) and `EventPort` (a Kafka client, chosen over Dapr in ADR-004), config from object storage that is checked by a schema and reloads with no restart, `/ready`, a graceful drain, and a read-only root on both containers. It builds on PoC-3's one front door, so idempotency (a key, a lease that a dead replica loses, and a cached result that any replica replays) is added once in `serve()` for every interface and engine. It shows this with Traefik in front of N pairs in Compose, a kill drill and a drain drill that lose no request, and container roles on kind, but throughput growth at 4 pairs stays flagged for a Linux host (122 X-5). It hands PoC-5 the stateless chassis, the kind cluster setup, and the drain and liveness rules that the remote lane and rolling restarts rely on. The rule later PoCs must keep: a replica holds nothing a retry needs, so all state goes through a port, idempotency and config fail closed, and `/ready` goes false before a replica stops taking requests.

## PoC-5: sandboxed (R5)

PoC-5 added the `remote` lane: the untrusted workload runs in its own gVisor pod, holds only its own token, and reaches only the chassis proxies, which check that token and a run in flight. It also added `spec.trust` with an admission policy, default-deny NetworkPolicy, `ToolPort` with a per-key allow-list in LiteLLM's MCP gateway, and a code runner that gives each call a fresh sandbox. It builds on PoC-2's a2a-sdk client and sidecar lane and on PoC-4's stateless chassis, and it runs both lanes on a kind cluster. It hands PoC-6 a remote lane that 6b fills with real engines, plus a kind harness and hostile suites that 6b reuses. The rule later PoCs must keep: every refusal is shown on a real cluster next to its allowed control, and only the chassis container holds a credential or a service account token.

## PoC-6: framework bake-off, 6a, 6b, 6c (R6)

PoC-6 ran eight engines on the same three tasks behind one chassis, using the `bakeoff` kit, and scored them in a scorecard and ADR-006 (still Proposed, with PydanticAI as the default). 6a ran the trusted engines in the sidecar and in-process lanes. 6b put the untrusted ones (smolagents, the Claude Agent SDK, kagent-adk) in PoC-5's remote lane on kind, and 6c ran every engine on a pre-trained SLM by changing only `spec.model.route`. It builds on PoC-5's remote lane, kind cluster, and hostile suites, and it adds the plain-A2A mode and the `/v1/messages` proxy route in contract v5. It hands PoC-7 a frozen `handle` contract and event schema (`schema_version` "0", pinned by `test_contract_freeze.py`), which contract v6 only adds to. The rules later PoCs must keep: an untrusted engine runs only in the remote lane, checked in the registry and again at config load (`spec.trust`), and a breaking change bumps the schema version and keeps "0" accepted.

## PoC-7: cross-cutting decisions (R7)

PoC-7 added security, observability, feedback, and evals once, at the chassis and LiteLLM: guardrail stages with a guardrail server, OTel export to Langfuse and Jaeger, a feedback route, and an evaluator gate, each behind a port with a fake and a contract suite. It builds on PoC-6's engines in every lane, its bake-off harness, and its eval trial, and it shows each concern on at least two engines with no engine-specific code. It hands PoC-8 four proposed ADRs (007 to 010), the Compose stack, and the open work: Langfuse scores from the gate, LiteLLM's Presidio hook, and a checked streamed answer. The rule later PoCs must keep: a cross-cutting concern lives in the chassis or a shared service, never in an engine, and only the workload's event mapping may differ per engine. Text that leaves the chassis, in spans, errors, or feedback, is redacted first.
